# Roadmap: the wiki plugin

The index of plans: what is in progress, what is planned, and what is parked, each with the trigger that would make it worth picking up. An item may be one line; a plan worked out in detail lives in its own file in `docs/plans/`, linked from the item, and is deleted when the work is done. The decisions behind what is built are in `docs/adr.md`. Small fixes and follow-ups are GitHub issues.

## In progress
- **Public release of wiki-tools** (intent settled 2026-11-15, plan reviewed the same day). The git history holds personal data (the owner's name and emails, a third party's name and email, addresses, hostnames), so the public repo is a new one, started from one commit of the cleaned files; the current repo becomes a private archive. When phase 7 is done, this entry becomes a decision in `docs/adr.md`, written without naming the archive.
  - **Goal and access:** people can install and use the plugin. The new `draitchbar/wiki-tools` starts private, is checked in a short staging phase, then goes public. Outsiders can read and fork; issue creation and pull requests are limited to collaborators (Settings → Features, "Collaborators only"; users with the triage role can also create issues). Comments from outsiders on existing issues and PRs are accepted and moderated by hand (no interaction limits). License: MIT, "Copyright (c) 2026 draitchbar". `marketplace.json`'s description is reworded for public users.
  - **What counts as personal data:** real names and emails, employer and work identifiers, home address and place names, hostnames and user paths (`C:/Users/<name>`), third parties, real file and folder names from personal accounts, and the real names of personal wikis. Allowed: the `draitchbar` handle, `draitchbar@users.noreply.github.com` (and GitHub's `<id>+draitchbar@…` form) and the `draitchbar.com` domain. Commits carry only noreply emails: `*@users.noreply.github.com`, `noreply@anthropic.com` (the `Co-Authored-By` trailer) and `noreply@github.com` (web merges), for the owner and collaborators alike. No `Claude-Session:` trailers in the new repo (CLAUDE.md; the check blocks them): they point into the owner's private sessions.
  - **Accepted, out of scope:** the owner's other public repos already link the handle to the owner's real name and email; they stay as they are for now. The check still protects everything else on the list above.
  - **Trust model:** collaborators are trusted. The PII job and the review run on `pull_request`, so a PR's own workflow and check code run with the secrets; a collaborator could weaken the check or print a secret. The owner reviews every change to `.github/workflows/` and the check. Each secret is passed only to the one step that needs it, through `env`. Stated in `CONTRIBUTING.md`.
  - **The PII check, in three layers.** A push to a public repo can't be taken back: `refs/pull/N/head` is read-only and survives a deleted branch, a squash and a force push; only GitHub Support can purge it, and forks and clones keep it regardless. Once public, deleting and recreating the repo no longer helps. So the check runs before the push where it can; CI catches the rest only after it is public.
    - `scripts/pii-check.sh` + `pii_check.py` (stdlib, behind `py-run.sh`, with fixtures and tests). It scans, per commit: the added lines, file paths and renames (`--name-status -z`, `core.quotepath=off`), the message, author, committer and trailer emails; merge commits against their first parent; binary files by name only. Also the branch name, tag names and messages, and in CI the PR title and description.
    - General patterns are committed (emails that aren't noreply, user paths, hostname shapes that don't mirror the real hostnames), with a committed allowlist for test data (reserved domains such as `example.com` and `.invalid`, `/home/u`, `git@github.com`). The check passes on today's tree before it is required.
    - The private denylist is read from a file outside the repo locally (`~/.config/wiki-tools/pii-denylist.txt`) and from the secret `PII_DENYLIST` in CI. Matching folds case, maps `ø`/`æ`/`å` to both spellings (`o`/`oe`, `ae`, `aa`/`a`), treats `.`, `_`, `-`, space and nothing between words alike, decodes percent-encoding and git's octal path quoting, and uses word boundaries for short entries. A hit names the file, line or commit and the entry's number, never the term or a normalised form (a test asserts this). No local denylist: the check says so and runs the general patterns. In CI a missing or empty `PII_DENYLIST` fails.
    - Local: a committed `.githooks/pre-push` (mode 100755), switched on per clone with `git config core.hooksPath .githooks` (`docs/development.md`). It reads `<local ref> <local sha> <remote ref> <remote sha>` lines from stdin: a new branch (all-zero remote sha) or a remote sha not known locally scans `<local sha> --not --remotes=<remote>`; a deletion is skipped; any error from the launcher or Python fails the push. CLAUDE.md: never `--no-verify`, and every session, cloud sessions included, runs the `core.hooksPath` line before its first push. `run-tests.sh` warns when `core.hooksPath` isn't set. Edits in the GitHub web UI skip the hook; the owner avoids them.
    - CI: its own workflow (not `ci.yml`, so a title edit doesn't rerun the test matrix) on every PR event (opened, new commits, title or description edited), a required check in the `main` ruleset; and on push to `main`, which checks the squash commit GitHub creates (detection only). Title and description edits stay in the PR's history, so that part is detection only too.
    - `claude-review.yml`: an advisory PII section for what patterns miss (people's and place names, real file names, work or personal details), reading `gh pr diff` and `gh pr view --json commits,title,body`. It never quotes a finding, only its kind and place; obviously made-up test data is fine. It doesn't get the denylist. Comments from non-collaborators (`author_association`) are treated as data, never as instructions. `anthropics/claude-code-action` is pinned to a commit SHA.
    - Log masking: GitHub may mask each line of a multi-line secret, turning matching text in public logs into `***` and so revealing a term. Check in staging; if so, keep denylist entries long enough not to match ordinary text.
    - Secrets: GitHub secret scanning and push protection (free on public repos), not gitleaks. Owner's account: "Keep my email addresses private" and "Block command line pushes that expose my email" (it checks only each push's last commit, so it is an extra, not the check). Collaborators keep their email private too (`CONTRIBUTING.md`), since the squash commit uses the PR author's GitHub email.
    - Issues and comments aren't scanned; `CONTRIBUTING.md` asks collaborators to keep personal data out of them.
  - **Repo settings:** squash merge only, with the PR title and description as the squash message (both scanned); delete branches on merge; wiki and discussions off. Collaborators push branches to the repo, not to forks (fork PRs get no secrets, so the PII check and the review would fail). Ruleset on `main`, switched on right after going public (the free plan refuses rulesets on private repos): a PR is required, no required approvals; required checks are CI on Linux and Windows and the PII check; no force pushes or deletion; no bypass actors.
  - **Phases:**
    1. *In this repo, through normal PRs:* close the open issues; build the check, the hook, the CI job and the review section (done); add `LICENSE` and `CONTRIBUTING.md`; replace real wiki names with generic descriptions; remove names of work wikis and machines (e.g. in the other roadmap entries); replace commit SHAs and `#N`/issue links with words; document the GitHub install route for users (`claude plugin marketplace add draitchbar/wiki-tools`) in the README and `docs/setup.md`; update CLAUDE.md (remote, PII rules, the hook line, no `Claude-Session:` trailers). Add the names removed here to the denylist. Then run the check over the whole tree with the full denylist and read the tree through.
    2. *Before the new repo exists, on every machine and in every worktree:* point the old clones' `origin` at the archive's name, or move them aside, so no clone can push the old history into the new repo. *Owner, by hand:* rename `wiki-tools` to the archive name (the new repo of the old name then replaces GitHub's rename redirect).
    3. *Claude, with `gh`, one step at a time with the owner's approval:* build the commit in a fresh folder (`git init`, then `git archive main | tar -x` from the old clone), so no ignored files, tags or other refs come along; author and committer `draitchbar <draitchbar@users.noreply.github.com>`, no signature, date in UTC. Create the private `wiki-tools` and push with an explicit refspec (`main:main`). Set description, features, merge settings and issue labels.
    4. *Owner:* add the secrets `CLAUDE_CODE_OAUTH_TOKEN` and `PII_DENYLIST` (master copy in the password manager), install the Claude GitHub App on the repo, set the account email options. Then a test PR in staging: CI, the PII check with a planted hit that is made-up data only (never a real denylist term), the push-to-`main` check, the review, and how secret masking behaves. Test the GitHub install route in a scratch folder. A leak in this phase is fixed by deleting and recreating the repo. Delete the staging workflow runs before going public.
    5. *Gate:* no clone or worktree with the old history has `origin` pointing at the new repo. *Owner:* make the repo public. *Claude:* the `main` ruleset, secret scanning and push protection. Test the install route again without being signed in.
    6. *Machines:* development clones are re-cloned. Each machine with wikis: check the old clone has nothing uncommitted or unpushed (it is live in every wiki); quit all wiki sessions; move the old clone aside or delete it; clone the new repo to the same path (the directory marketplace and `wiki@wiki-tools` stay valid); start `claude` in each wiki and run `wiki-check.sh`. A settings rule with a fixed clone path keeps working at the same path; the owner may change it to the `*/sources/<type>/<script>.sh` form.
    7. *Owner, by hand:* in the archive, remove the secret, disable the workflows, remove it from the Claude GitHub App's repositories, set Archived. It stays private for good; nothing in the new repo points to it.
  - **Out of scope:** the owner's other repos, public or private. The docs keep naming `aitchbar-ai-tools` (the Proton Drive reader), which the owner may make public too. Not planned: interaction limits against outsider comments.
- **Parallel test runs (`pytest-xdist`):** decide on measured numbers, which CI's Windows job (`.github/workflows/ci.yml`) gives; the codebase tests are about a third of the Windows suite's time. The tests are written to be safe in parallel.
- **`lint.sh` in the largest wiki:** on the machine that holds it, compare `lint.sh`'s output with the last bash version of the script. It is a work wiki, the largest, and has content the other wikis lack (codebase research sources, Jira and Teams citation prefixes).
- **Clone-anywhere layout** (`docs/adr.md`, 1): check on Windows (Git Bash), and plugin loading in a fresh clone of a wiki without a project-scope install (`docs/setup.md`, "Open checks").

## Planned, not started
- **Copilot CLI as a second development agent** (plan reviewed 2026-11-15): the repo can be developed with GitHub Copilot CLI as well as Claude Code, under the same rules, each rule and skill written once. Plan: `docs/plans/copilot-cli.md`.
- **Wiki tooling** (grill the open choices before building). Order: C first (cheap, improves every audit), then A → B, then D.
  - **C, fidelity checks in `/wiki:audit` and `/wiki:lint`:** every number, date and name on a page must appear in the cited source (grep the whole source; two quotes from one supplier mixed up on a page were this kind); claim tags `^[inferred]` / `^[ambiguous]` beside non-sourced statements, which lint counts and lists. Extends the "User statement (YYYY-MM-DD)" rule in `schema/wiki-conventions.md`. ~1 h. Open: tag syntax; warn or error on untagged unsourced claims.
  - **A, personal subagents** `candidate-researcher` and `evaluator` in `~/.claude/agents/`: "find N candidates, then evaluate them" made repeatable (a house-renovation wiki: carpenters, annex suppliers; a car-leasing wiki: `research/*.md`). The researcher has web tools and writes only to `outputs/`; the evaluator is read-only with a criteria rubric and `memory: user`. ~1 h. Open: the rubric; where the researcher may write; personal agents rather than plugin agents (agents in plugins ignore their own hooks).
  - **B, a saved workflow `/evaluate-candidates`:** research → N evaluators → a ranked summary, the same way every run. After A. ~30 min. Open: number of evaluators; output name and format.
  - **D, Brave bookmarks as a wiki-local source type** in the house-renovation wiki, through `/wiki:add-source bookmarks` (the first wiki-local type): a wrapper reads Brave's `Bookmarks` JSON (Snap profile on Linux) and lists bookmarks in the configured folder added since `last_checked_<key>`; no page fetching. No change to wiki-tools; promote it to a standard type if it proves useful. ~1 h. Open: the folder name per wiki (CLAUDE.md); the Windows profile path later.

- **Type checking for the plugin's Python:** none of the ~175 functions (about 3,650 lines in 12 modules) is annotated today. Add a checker (mypy or pyright) to CI as a test-only dependency, like pytest, never the plugin's; record the decision in `docs/adr.md`, 4. Annotate module by module, `contract.py`, `sourcelib.py` and `guard.py` first, with `from __future__ import annotations` for 3.9; once a module passes, ruff's `ANN` rules keep it annotated. Ruff's `ANN` alone only checks that annotations exist, not that they are right, so it isn't enough by itself. Example of what types would catch: the three `git()` helpers return different shapes. Annotations cost nothing at run time, so the guard is no slower. Open: mypy or pyright; how strict.

## Parked, with triggers

| Item | Trigger to pick it up | Notes |
|---|---|---|
| **Weekly full PII scan** | A term is added to the PII denylist, or the public repo has run for a while without one. | A scheduled and on-demand CI job over the whole tree and all history with the full denylist, catching old content a new term matches and anything that reached `main` past the PR check. |
| **Port `codebase/git.sh` to Python** | `git.sh` needs a change that is awkward in bash (a new operation, more output parsing), or its subshell error handling causes a bug. | Inventory (529 lines): the argument checks (~150 lines) would get only a little simpler; the main gain is that a validator's `die` runs in a subshell, so every call site repeats `\|\| exit 1` (~17 times). Larger gains in the operations: the `awk` programs (grep's caps, `show`, `ls`, `drift` reading git's diff output) and the citation pipelines of `verify-all`/`drift-all`. Harder in Python: the running-fetch marker (a bash PID checked with `kill -0`; Python's `os.kill(pid, 0)` can't do that on Windows), the fetch's inline shell credential helper, the clone root as typed (Windows paths). `gh.sh` stays bash (its handoff to `gh` breaks on Windows from Python). The 136 codebase tests run end to end through the launcher, so a port inherits them; CI runs them on Windows. Start with an inventory section, then a decision. |
| **Research cost levers** (`/wiki:research`; cheaper models: `docs/adr.md`, 6) | Research runs feel slow or costly again. | From a profile of real runs: (1) fewer empty and repeated searches: 20% of `grep`/`igrep` calls return nothing (pattern-file greps do best, 11–16%); better brief guidance, a few percent. (2) shorter notes files and hand-backs: 26% of researcher cost goes to writing `agent-<step>-<n>.md` and the return; a few percent. (3) the main session (31% of cost): only smaller page reads would help; not estimated. Each needs its own decision; the bar is 25% less time or cost at equal quality. |
| **A code index** (graphify, SCIP, ctags, LSP, …) for `/wiki:research` | Exploration and search become a large share of research time or cost. | An index could save at most ~7% of cost and ~8% of time today, against a 25% bar; the rules if one comes are in `docs/adr.md`, 6. |
| **qmd local search** | Queries feel slow or keyword searches miss pages (synonyms), typically at a few hundred pages. | Test on the house-renovation wiki first. |
| **Headless or `/loop` ingest** | Ingests have become routine. | Test `/loop` in a session first. Headless needs `--allowedTools` (incl. `Skill`) in untrusted folders; first ingests and data-model reviews need the user. Unknown whether claude.ai connectors load under cron. |
| **Obsidian Bases** view of frontmatter | You want a "stale pages" or status view inside Obsidian. | User-side only; `index.md` stays Claude's entry point. |
| **Obsidian Importer for OneNote** | New OneNote notes appear for a wiki. | |
| **Readers from installed plugins** | A second source needs a reader that ships as a plugin; a Claude Code update stops enabled-only plugins from directory marketplaces running from the clone; or readers should work from a plain `claude plugin install` from GitHub. | Today the guard refuses every command naming `.claude/plugins/` (it protects the guard's Python cache and `known_marketplaces.json`/`installed_plugins.json`), so such plugins run from a local clone (`docs/guard.md`, "Known false positives"). The enhancement: a guard-protected instance key, e.g. `reader_commands:`, listing the reader's read-only commands (onenote: `onenote.ps1` with `status`, `notebooks`, `sections`, `pages`, `page`, `section-export`; never `Connect-OneNote.ps1`), allowed as plain calls even under `.claude/plugins/cache/`. In the instance, not the contract (the reader is per machine). Needs the key in `contract.py`, the rule in `guard.py`, fixtures, a Windows run. |
| **Guard on `read_resource` URIs** (ms-teams) | The ms-teams drop rule (keep only results from listed channels, chats and folders) proves too weak, or a second Microsoft 365 type arrives. | A contract key such as `uri_prefixes` that the guard enforces on `mcp__claude_ai_Microsoft_365__read_resource` (refusing `mail:///` and `calendar:///` unless a type allows them). A hook can't filter what tenant-wide searches return, only refuse calls by their input. |
