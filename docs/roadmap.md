# Roadmap: the wiki plugin

The index of plans: what is in progress, what is planned, and what is parked, each with the trigger that would make it worth picking up. An item may be one line; a plan worked out in detail lives in its own file in `docs/plans/`, linked from the item, and is deleted when the work is done. The decisions behind what is built are in `docs/adr.md`. Small fixes and follow-ups are GitHub issues.

## In progress
- **Clone-anywhere layout** (`docs/adr.md`, 1): one check left, a wiki's wrapper rule `Bash(bash */sources/<type>/<script>.sh *)` matching without a prompt on Windows (Git Bash), in an interactive session outside auto mode (`docs/setup.md`, "Open checks").

- **Unattended ingest, `/wiki:clarify`** (`docs/adr.md`, 12): the user's live check in a wiki: an unattended ingest that raises each kind of question, `/wiki:clarify` answering and dismissing, and how `^[open: …]` renders in Obsidian (Live Preview, reading view, a table cell).
- **Wikis in a Claude Code cloud session** (decisions: `docs/adr.md`, 17 to 20; guided setup in `plugins/wiki/cloud/SETUP.md`; [remaining live checks](plans/cloud-wikis.md)): the environment's setup script clones wiki-tools and `CLAUDE_CODE_PLUGIN_DIRS` loads the plugin, which updates itself at session start; skills, schema, sync status, the guard, connector sources, saving to the default branch and a routine's unattended ingest work. Next: the live checks (a failing setup script, self-update from a stale snapshot, the routine's save, the connectors' deny in a routine, typing skills on the phone, the git identity). Open work they found: classifying the cloud-only tools in the guard; `platforms` in the cloud (`sources.sh` reports a source with a local reader as available); the `ms-teams` folder snapshot lost with each VM; two machines ingesting the same source; the environment's Stop hook asking to push the session branch; Proton Drive.

## Planned, not started
- **OneNote ingested unattended, without the user's machine** ([plan](plans/onenote-cloud.md), 2026-11-27): a cloud session can't hold a OneNote credential safely (Graph's OneNote API takes only delegated tokens since 2025-03-31, and anything in the VM is readable by the model). So `onenote` runs in a GitHub Actions workflow on the wiki repo: a pre-step signs in to Azure through OIDC, refreshes the token from Key Vault and writes it back, and hands Claude only a one-hour access token; `actions/cache` keeps the snapshots; it saves through `save.sh`. Cloud routines keep the connector sources. Spike first: Conditional Access from a runner, a headless skill start, the guard on the runner, `save.sh` with the job token. Fallbacks: a network secret, a token broker. Separately: `sources.sh` reports `onenote` as available in a cloud session.
- **Connector tools opt-in** (from PR review, 2026-11-24): today every MCP tool passes the guard unless a reader binding limits it or a settings rule denies it, and denying a connector's write tools means naming each one (a list that breaks when a connector renames or adds a tool, and misses new connectors: Google Calendar, Meetings, Claude Docs and Claude Data were all offered, unasked, in a cloud session). Turn it around: the guard refuses any MCP tool the wiki hasn't opted into, through a source's reader binding or an explicit list of extra tools in a protected file. A helper step lists the session's MCP tools and proposes which to opt into, and the user approves and pastes, as with `/wiki:bind-reader`; read-only is the model's judgement, so the user's approval is what counts. Open: where the list lives (settings rules or a source-like file the guard reads), the cloud's other tool names (the pair table, `docs/adr.md`, 17), and the wikis' current connectors on migration. Replaces naming write tools one by one; the GitHub refusal (`docs/adr.md`, 3) stays either way.
- **Copilot CLI in existing wikis:** [design](copilot-wiki-design.md) and [step-by-step plan](plans/copilot-wiki-support.md). Three parts: a spike that collects real compatibility evidence and revises the plan (Linux evidence collected and reviewed by Copilot 2026-11-17, including autopilot with `--allow-all`, the mode Copilot will run in, the Windows observations for part C, and on 2026-11-18 assisted approval and manual-only skills); part B builds on the guard as #24 left it (every tool through the guard, unknown names refused, so Copilot's own tool names need classifying); the first delivery, the shared-plugin migration plus `raw` and `local-folder` for Copilot on Linux, with a small real-client smoke set and Claude regression on Linux and Windows; then Copilot on Windows. Switching sessions needs no content/state migration.
- **A `gws` reader plugin for Gmail and Google Drive:** a read-only reader around the Google Workspace CLI (`gws`) in a separate plugin, like the `proton` reader, so wiki-tools doesn't depend on `gws`. The `google-drive` contract is tool-neutral already (2026-11, `docs/adr.md`, 10); `gmail` is tool-neutral (`access: tools`) too, and already on date state (an overlap window, thread IDs from the sync log) and read-only (2026-11, ADR 10); both still get `guard_words: gws` with the reader, so a wiki session reaches Google only through it (no direct `gws`, no `gws auth`). Read-only at Google: `gmail.readonly` and `drive.readonly`. The reader's **status** checks the scopes actually granted (a broader earlier token can survive `--readonly`) and a minimum `gws` version (pre-1.0). It protects `~/.config/gws/` with its own hook. Independent of the Copilot migration: used in Claude first, then the route to Gmail and Google Drive in Copilot ([plan](plans/copilot-wiki-support.md#gmail)). Hosting a second reader plugin is the trigger for the parked **Readers from installed plugins**. The claude.ai Google Drive and Gmail connectors stay allowed readers, bound per instance.

- **A Teams reader plugin for `ms-teams`** ([spike plan](plans/teams-reader-plugin.md), 2026-11-26, cut down 2026-11-28): the Teams half of the parked **Reader plugins for connector workarounds**. A spike, nothing merged, for a second plugin `teams-reader` in this marketplace, enabled only in wikis with a Teams instance, that carries no code: only the connector's operation mapping, denies and quirks, as notes the model loads. The folder walk and the snapshot stay in the core, a generic mechanism (`docs/adr.md`, 10), so the spike needs no launcher across layouts and no guard exception. It depends on `wiki` (never the reverse, through `plugin.json`'s `dependencies`) and keeps today's protections exactly. A reader adds to the guard and the settings only as data in a manifest whose format the core defines (dependency inversion; no reader guard hook, since a hook's deny can add refusals but never exceptions); settings rules reach the wiki through the binding, and bind-reader finds the notes by plugin name, never by a skill's description. The guard doesn't change: it already protects a reader's folder in every layout (checked first, with one gap when the config or cache folder sits outside `.claude`), and a missing reader stops its instance at Check, not the whole wiki. Finding a reader at hook time waits for the first reader with guard fields. First, on its own: a binding field for auxiliary rules (the snapshot allow, OneNote's reader rules), emitted by `sources.sh settings` and checked by `check-settings`. Then two plugins per wiki, how `/wiki:bind-reader` and an ingest find the notes, version skew, a Teams-only cloud routine and migration; a `teams-reader` README with the enabling flow; automated e2e tests in CI and live runs in throwaway wikis on Linux and Windows. No-go keeps the notes in the contract. Readers that bring code (launcher, trusted reader root) are left to their own plans.

- **Windows test run within 1:30** (issue #123, follow-up to #115 and #119, 2026-11-27): after #119 (save tests from a copied template, split in three) the Windows jobs take 1:34–2:18 plain and 2:39–3:41 e2e, against a budget of 1:30 on two consecutive runs. The run is now bound by total work over the runner's 4 CPUs, not by one module, so about 40 % of the work has to go plain and 60 % e2e. Steps: profile 2–3 Windows runs with the per-module summary and `--durations=20`, and record the numbers in the issue; review every module for slop, obsolete, redundant and too-narrow tests, never leaving a guard check or a `save.sh` refusal without a test. Open choices for the plan: Defender real-time scanning off on the Windows runner (a workflow change, the owner's call); fewer git calls in `save.py` (about 17 per run); guard fixtures in-process under `--e2e`, keeping the `hooks.json` launcher tests (`test_guard.py` sums to about 136 s e2e against 30 s plain, but this weakens the guard's e2e path). A CI or distribution change amends `docs/adr.md`, 6.

- **A wiki as a research source for another wiki** ([design](plans/wiki-source.md), 2026-11-23): `/wiki:research` in one wiki drives the other wiki's agent as a ReAct action, started on demand by a narrow wrapper, under that wiki's own guard and opt-in policy. A proof of concept as a wiki-local type, with no plugin change and a gate of live checks: first a read-only agent over the other wiki's pages and `raw/`, then its connector sources.

- **Wiki tooling** (grill the open choices before building). Order: C first (cheap, improves every audit), then A → B, then D.
  - **C, fidelity checks in `/wiki:audit` and `/wiki:lint`:** every number, date and name on a page must appear in the cited source (grep the whole source; two quotes from one supplier mixed up on a page were this kind); claim tags `^[inferred]` / `^[ambiguous]` beside non-sourced statements, which lint counts and lists. Extends the "User statement (YYYY-MM-DD)" rule in `schema/wiki-conventions.md`. ~1 h. Open: tag syntax; warn or error on untagged unsourced claims.
  - **A, personal subagents** `candidate-researcher` and `evaluator` in `~/.claude/agents/`: "find N candidates, then evaluate them" made repeatable (a house-renovation wiki: carpenters, annex suppliers; a car-leasing wiki: `research/*.md`). The researcher has web tools and writes only to `outputs/`; the evaluator is read-only with a criteria rubric and `memory: user`. ~1 h. Open: the rubric; where the researcher may write; personal agents rather than plugin agents (agents in plugins ignore their own hooks).
  - **B, a saved workflow `/evaluate-candidates`:** research → N evaluators → a ranked summary, the same way every run. After A. ~30 min. Open: number of evaluators; output name and format.
  - **D, Brave bookmarks as a wiki-local source type** in the house-renovation wiki, through `/wiki:add-source bookmarks` (the first wiki-local type): a wrapper reads Brave's `Bookmarks` JSON (Snap profile on Linux) and lists bookmarks in the configured folder added since `last_checked_<key>`; no page fetching. No change to wiki-tools; promote it to a standard type if it proves useful. ~1 h. Open: the folder name per wiki (CLAUDE.md); the Windows profile path later.
