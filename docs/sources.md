# Sources

How the wikis read their sources: types, instances, and how to add one. The reasons behind the design are in `docs/adr.md`, 2 and 5.

## Types and instances

The wiki skills know no particular source. They talk to every source through its **contract**.

- **Source type**: a `SOURCE.md` contract (template: `plugins/wiki/templates/source-type/SOURCE.md`). Frontmatter (flat, bash-parseable): access kind, platforms, the parameters an instance must supply, the state it needs, `cite_prefix`, allowed read and bookkeeping tools, forbidden tools, guard words and wrapper scripts. Body: one section per operation, **Check**, **List new**, **Fetch**, **Mark ingested**, **Cite**, **Resolve citation**, plus **Caveats**.
  - **Standard types** live in `plugins/wiki/sources/<type>/`: `gmail`, `google-drive`, `ms-teams`, `jira`, `proton-files`, `local-folder`, `codebase`, `onenote`. `gmail` (tool-neutral, below; seen working with the claude.ai Gmail connector, connected once in claude.ai and then on every platform) ingests the threads under an instance's `labels`, `senders` and `recipients`, read-only, with a date state (a 7-day overlap, thread IDs in the sync log). `ms-teams` (tool-neutral, below; seen working with the claude.ai Microsoft 365 connector, connected once in claude.ai and then on every platform) needs, for that connector, the Graph permissions `ChannelMessage.Read.All`, `Channel.ReadBasic.All`, `Chat.Read` and `Files.Read.All` or `Sites.Read.All` granted to the Microsoft 365 connector; `Team.ReadBasic.All` is usually missing and not needed (take a team id from the `groupId=` part of a channel link). `jira` (tool-neutral, below; seen working with the claude.ai "Atlassian MCP" connector) ingests the issues matched by an instance's named `scopes` (clauses AND-ed within a scope, scopes OR-ed; a new scope is backfilled) into project pages; comments and remote links only when needed; attachments aren't downloaded. `google-drive` (tool-neutral, below; seen working with the claude.ai Google Drive connector, connected once in claude.ai and then on every platform) ingests the files below an instance's `folders` (`<folder path> (<folder id>)`, subfolders included), with a date state; formats it can't read as text are downloaded into the cache.
  - **Local types** live in a wiki's `.claude/sources/types/<type>/`. They may ship wrapper scripts and have no test harness. A local type can't reuse a standard type's name.
- **Source instance**: a wiki's use of a type, `.claude/sources/instances/<key>.md` (type, parameters, agreed state fields). The key is the `/wiki:ingest <key>` argument and names the state lines (`last_checked_<key>`, ...) in `raw/sync-log.md`. One wiki may have several instances of one type. `raw` (built in) and `all` (`/wiki:ingest all`) are reserved and can't be instance keys.
- **Manual key**: a `last_checked_<key>` line with no instance file (e.g. `web`). Its material enters via `raw/` or as user statements; sync-status and `sources.sh list` show it, `/wiki:ingest` can't read it, and lint accepts citations starting `<key>:`. Add one with `/wiki:add-source manual <key>`.
- **Research types** (`mode: research`, e.g. `codebase`): a source too large or too fast-moving to ingest. `/wiki:ingest` refuses it and sync-status leaves it out; `/wiki:research <key> "<question>" [--critique] [--worktree]` researches it on demand. The main session plans and dispatches up to 10 `wiki:source-researcher` agents per step (at most 5 steps), with notes in `~/.cache/wiki-sources/<wiki>/<key>/runs/`; an optional `wiki:critic` checks every claim through its own agents (at most 3 rounds). Findings are merged into existing pages, cited at a pinned commit. With `agent_only: yes` the main session can't read the source at all (the guard blocks its Read, Grep and Glob there, and every wrapper operation outside the contract's `main_ops`); only subagents can. The shared schema tells wiki sessions to check such citations for drift before answering from them. The `codebase` type needs a local git clone of the repository (a shallow clone works, with history only from its boundary) and, for PR and issue context, `gh` logged in with an account that can read the repository (`gh_user`; the wrapper never switches the active account).
- **Tool-neutral types** (`access: tools`, e.g. `onenote`, `proton-files`, `jira`, `google-drive`, `ms-teams`, `gmail`): the contract names no tools. It lists the operations it needs (list sections, list pages, read a page, ...) and the session uses whatever this machine supplies for them: a CLI, a skill or an MCP server. Its contract allows no tools (only its own cache folder may be allowed); the allow and deny rules come from each instance's binding (below). How read-only is kept is in its Caveats: for `onenote` **the connection's scope** (Graph `Notes.Read`; Check reports the scope and warns if it can write); for `proton-files`, since Proton has no read-only sign-in, **the reader's read-only operations** (the `proton` plugin's `drive.sh` and its own hook), while the contract still denies and guards the `proton-drive` CLI itself (`forbidden_tools`, `guard_words`), so only the reader reaches it; for `jira`, `google-drive`, `ms-teams` and `gmail` **the connection's access or scope** (`drive.readonly` for Drive and `gmail.readonly` for Gmail, where the reader can have them; the Graph read permissions for Teams) **and the deny rules for the reader's write tools** (the instance's `reader_deny`). `proton-files` ingests the files below an instance's `roots`, which the session passes to the reader on every call (a reader-side check, weaker than the wrapper that read them from the instance before 2026-11-07). `onenote` ingests the pages of the OneNote sections (tabs) an instance names as `Notebook > [Group > …] Section` paths, with a cursor on the section modified time and a text snapshot per page, so edited pages come back (page modified times from Graph can't be trusted); Linux and Windows, wherever the reader works. **Binding:** `/wiki:add-source` records which reader the user means to use; `/wiki:bind-reader <key>` then tests it, following the contract's `## Bind` section, and drafts the instance's binding: a `reader` list in the frontmatter (`<operation>: <tool>`, unquoted: frontmatter lists are read literally, not as YAML, and a quoted item is refused; the operations as the contract's `operations` names them; a dispatcher with a `<field>=<value>` limit such as `name=listJiraProjects`), a `reader_deny` list of the reader's write tools, and a `## Reader` section with the fixed arguments. Instance validation checks the binding; `sources.sh settings` and `check-settings` give its allow and deny rules (met in the wiki's or your user settings); the guard refuses a limited tool called with another value, which no settings rule can express (`docs/adr.md`, 13). Every ingest follows the binding; Check starts `/wiki:bind-reader` when there is no `reader` list or it names a tool that's gone (for `ms-teams` also when an operation a parameter the instance uses needs is unbound). A new connector or reader is therefore a new instance file, not a new contract.
- **Moving a `google-drive` instance to the tool-neutral contract** (2026-11): `folders`, the state and the citations are unchanged. Until the instance is bound, Check stops and starts `/wiki:bind-reader <key>`; install the instance file it drafts (with `reader`, `reader_deny` and `## Reader`). Before its tests, add a deny for the connector's `request_access` (new) and keep the other write-tool denies and `get_file_permissions`, which now come from `reader_deny`; remove the old allow for `list_recent_files`, which nothing uses (`check-settings` reports missing rules, not extra ones).
- **Moving an `ms-teams` instance to the tool-neutral contract** (2026-11): `channels`, `chats`, `folders`, the state and the citations are unchanged. Until the instance is bound, Check stops and starts `/wiki:bind-reader <key>`; install the instance file it drafts (with `reader`, `reader_deny` and `## Reader`). Before its tests, add denies for the connector's Outlook and people tools (new) and keep the five write-tool denies, which now come from `reader_deny`; keep the connector's read allows, which now come from the binding (`check-settings` lists any that are missing); remove the old allow for `snapshot.sh` (`check-settings` reports missing rules, not extra ones); add the allow `Bash(bash */scripts/file-snapshot.sh *)`, which `/wiki:bind-reader` hands over from the contract's `## Bind` for an instance with `folders` when the reader's folder listing has no modified times (the folder snapshot is now the shared `file-snapshot.sh`, used only when the reader's folder listing has no modified times); keep the `walk.tsv` Edit allow; remove the allows for the connector tools no longer bound (`get_me`, now denied, `teams_list_teams` and `sharepoint_folder_search`).
- **Moving a `gmail` instance to the tool-neutral contract** (2026-11): `labels`, `senders`, `recipients`, `exclude`, `last_checked` and the citations are unchanged; Gmail is now read-only (`docs/adr.md`, 23). Until the instance is bound, Check stops and starts `/wiki:bind-reader <key>`; install the instance file it drafts (with `reader`, `reader_deny` and `## Reader`). Before its tests, remove the old allows for the connector's `create_label` and `label_thread` (`check-settings` fails "in both allow and deny" while one stays beside its deny) and add denies for `create_label`, `label_thread`, `label_message`, `apply_sensitive_message_label`, `apply_sensitive_thread_label`, `list_drafts` and `get_draft`; keep the old denies and the read allows, which now come from the binding; add the allow for `download_gmail_attachment` if it is bound. No state moves: `last_checked_<key>` stays, and while the `wiki-ingested/<wiki>` label exists, searches keep `-label:wiki-ingested-<wiki>` so the threads it marks stay out; nothing new is labeled, and you may delete the label in Gmail whenever you like (a pre-move thread inside the 7-day window may then come back once; compare it with the pages' `sources:`). A wiki used locally and in a cloud session binds again when it switches.
- **Read-only by contract** (except `access: tools`, above). The only writes a type may declare are narrow bookkeeping; no standard type declares one, and a wiki-local type may. The guard reads every contract and instance at hook time; `.claude/sources/` and `plugins/wiki/sources/` are protected, so Claude drafts these files and you save and commit them.

**Add a source to a wiki**: `/wiki:add-source <type> [key]` in the wiki. It reads the contract, asks for the parameters, agrees the state, and drafts the instance file, the CLAUDE.md line, the sync-log line and the settings rules (`sources.sh settings <type> --key <key>`; cache rules come narrowed to `~/.cache/wiki-sources/<wiki>/<key>/`), and checks your edited settings with `sources.sh check-settings`. For a type that doesn't exist, it drafts a local type with you. You install each drafted file yourself, one at a time, in a separate terminal, not with Claude Code's `!` prefix (Git Bash on Windows): `bash ~/src/wiki-tools/plugins/wiki/scripts/install-source-file.sh instances/<key>.md < <file>` (or paste and Ctrl-D, which can break long lines), review the diff, `y`. It checks the file first and lists missing settings rules; it never commits.

**Add or promote a standard type**: in a session here, `/new-source-type <type>` or `/new-source-type promote <wiki path> <type>`. It researches the connector or CLI read-only, fills the contract, writes the wrapper, tests and guard fixtures, and ends with a green `run-tests.sh`. Promotion is your call, when a local type has proved useful.

`bash <plugin>/scripts/sources.sh list|show <key>|due|catalog|contract <type>|settings [<type>... [--key <key>]]|check-settings`, run in a wiki, shows what the skills see. `due` is what `/wiki:ingest all` ingests: every source last checked before today, oldest first (`raw` only when sync-status doesn't find it unchanged); the rest under Not due (checked today, nothing new in `raw/`) or Skipped, with the reason (research, `never`, **Check needed**, invalid, not available on this platform, manual key, unreadable date).
