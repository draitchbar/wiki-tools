# Sources

How the wikis read their sources: types, instances, and how to add one. The reasons behind the design are in `docs/adr.md`, 2 and 5.

## Types and instances

The wiki skills know no particular source. They talk to every source through its **contract**.

- **Source type**: a `SOURCE.md` contract (template: `plugins/wiki/templates/source-type/SOURCE.md`). Frontmatter (flat, bash-parseable): access kind, platforms, the parameters an instance must supply, the state it needs, `cite_prefix`, allowed read and bookkeeping tools, forbidden tools, guard words and wrapper scripts. Body: one section per operation, **Check**, **List new**, **Fetch**, **Mark ingested**, **Cite**, **Resolve citation**, plus **Caveats**.
  - **Standard types** live in `plugins/wiki/sources/<type>/`: `gmail`, `google-drive`, `ms-teams`, `jira`, `proton-files`, `local-folder`, `codebase`, `onenote`. `gmail`, `google-drive` and `ms-teams` need their claude.ai connector connected once (Settings → Connectors); it then works on every platform. `ms-teams` also needs the Graph permissions `ChannelMessage.Read.All`, `Channel.ReadBasic.All`, `Chat.Read` and `Files.Read.All` or `Sites.Read.All` granted to the Microsoft 365 connector; `Team.ReadBasic.All` is usually missing and not needed (take a team id from the `groupId=` part of a channel link). `jira` (tool-neutral, below; seen working with the claude.ai "Atlassian MCP" connector) ingests the issues matched by an instance's named `scopes` (clauses AND-ed within a scope, scopes OR-ed; a new scope is backfilled) into project pages; comments and remote links only when needed; attachments aren't downloaded.
  - **Local types** live in a wiki's `.claude/sources/types/<type>/`. They may ship wrapper scripts and have no test harness. A local type can't reuse a standard type's name.
- **Source instance**: a wiki's use of a type, `.claude/sources/instances/<key>.md` (type, parameters, agreed state fields). The key is the `/wiki:ingest <key>` argument and names the state lines (`last_checked_<key>`, ...) in `raw/sync-log.md`. One wiki may have several instances of one type.
- **Manual key**: a `last_checked_<key>` line with no instance file (e.g. `web`). Its material enters via `raw/` or as user statements; sync-status and `sources.sh list` show it, `/wiki:ingest` can't read it, and lint accepts citations starting `<key>:`. Add one with `/wiki:add-source manual <key>`.
- **Research types** (`mode: research`, e.g. `codebase`): a source too large or too fast-moving to ingest. `/wiki:ingest` refuses it and sync-status leaves it out; `/wiki:research <key> "<question>" [--critique] [--worktree]` researches it on demand. The main session plans and dispatches up to 10 `wiki:source-researcher` agents per step (at most 5 steps), with notes in `~/.cache/wiki-sources/<wiki>/<key>/runs/`; an optional `wiki:critic` checks every claim through its own agents (at most 3 rounds). Findings are merged into existing pages, cited at a pinned commit. With `agent_only: yes` the main session can't read the source at all (the guard blocks its Read, Grep and Glob there, and every wrapper operation outside the contract's `main_ops`); only subagents can. The shared schema tells wiki sessions to check such citations for drift before answering from them. The `codebase` type needs a local git clone of the repository (a shallow clone works, with history only from its boundary) and, for PR and issue context, `gh` logged in with an account that can read the repository (`gh_user`; the wrapper never switches the active account).
- **Tool-neutral types** (`access: tools`, e.g. `onenote`, `proton-files`, `jira`): the contract names no tools. It lists the operations it needs (list sections, list pages, read a page, ...) and the session uses whatever this machine supplies for them: a CLI, a skill or an MCP server. Its contract allows no tools (only its own cache folder may be allowed); the allow and deny rules come from each instance's binding (below). How read-only is kept is in its Caveats: for `onenote` **the connection's scope** (Graph `Notes.Read`; Check reports the scope and warns if it can write); for `proton-files`, since Proton has no read-only sign-in, **the reader's read-only operations** (the `proton` plugin's `drive.sh` and its own hook), while the contract still denies and guards the `proton-drive` CLI itself (`forbidden_tools`, `guard_words`), so only the reader reaches it. `proton-files` ingests the files below an instance's `roots`, which the session passes to the reader on every call (a reader-side check, weaker than the wrapper that read them from the instance before 2026-11-07). `onenote` ingests the pages of the OneNote sections (tabs) an instance names as `Notebook > [Group > …] Section` paths, with a cursor on the section modified time and a text snapshot per page, so edited pages come back (page modified times from Graph can't be trusted); Linux and Windows, wherever the reader works. **Binding:** `/wiki:add-source` records which reader the user means to use; `/wiki:bind-reader <key>` then tests it, following the contract's `## Bind` section, and drafts the instance's binding: a `reader` list in the frontmatter (`<operation>: <tool>`, the operations as the contract's `operations` names them; a dispatcher with a `<field>=<value>` limit such as `name=listJiraProjects`), a `reader_deny` list of the reader's write tools, and a `## Reader` section with the fixed arguments. Instance validation checks the binding; `sources.sh settings` and `check-settings` give its allow and deny rules (met in the wiki's or your user settings); the guard refuses `reader_deny` tools and a limited tool called with another value (`docs/adr.md`, 13). Every ingest follows the binding; Check starts `/wiki:bind-reader` when there is no `reader` list or it names a tool that's gone. A new connector or reader is therefore a new instance file, not a new contract.
- **Read-only by contract** (except `access: tools`, above). The only writes a type may declare are narrow bookkeeping (Gmail's `wiki-ingested/<wiki>` label). The guard reads every contract and instance at hook time; `.claude/sources/` and `plugins/wiki/sources/` are protected, so Claude drafts these files and you save and commit them.

**Add a source to a wiki**: `/wiki:add-source <type> [key]` in the wiki. It reads the contract, asks for the parameters, agrees the state, and drafts the instance file, the CLAUDE.md line, the sync-log line and the settings rules (`sources.sh settings <type> --key <key>`; cache rules come narrowed to `~/.cache/wiki-sources/<wiki>/<key>/`), and checks your edited settings with `sources.sh check-settings`. For a type that doesn't exist, it drafts a local type with you. You install each drafted file yourself, one at a time, in a separate terminal, not with Claude Code's `!` prefix (Git Bash on Windows): `bash ~/src/wiki-tools/plugins/wiki/scripts/install-source-file.sh instances/<key>.md < <file>` (or paste and Ctrl-D, which can break long lines), review the diff, `y`. It checks the file first and lists missing settings rules; it never commits.

**Add or promote a standard type**: in a session here, `/new-source-type <type>` or `/new-source-type promote <wiki path> <type>`. It researches the connector or CLI read-only, fills the contract, writes the wrapper, tests and guard fixtures, and ends with a green `run-tests.sh`. Promotion is your call, when a local type has proved useful.

`bash <plugin>/scripts/sources.sh list|show <key>|catalog|contract <type>|settings [<type>... [--key <key>]]|check-settings`, run in a wiki, shows what the skills see.

## Proton Drive CLI

The reader for the `proton-files` type, its CLI's recorded syntax, the CLI's setup and the reader's tests live in the `proton` plugin of `draitchbar/aitchbar-ai-tools` (`plugins/proton/README.md`; its design, the decisions and the hardening backlog in `docs/proton-design.md` there), since 2026-11-07.
