# Architecture decisions: the wiki plugin

The decisions behind how wiki-tools is built, and why. Plans and parked work are in `docs/roadmap.md`; how to use the plugin is in README.md and the pages it links.

## 1. One plugin, enabled per wiki, runnable from any clone
**Decision.** wiki-tools is a local-directory marketplace with one plugin, `wiki`. Each wiki enables it in its own `.claude/settings.json`, never at user scope. Everything the wikis need lives under `plugins/wiki/`. Skills and hooks name plugin files through `${CLAUDE_PLUGIN_ROOT}`; scripts find their own folder; the wikis' settings use path-free wildcard rules (`Bash(bash */sources/<type>/<script>.sh *)`). The shared schema (`schema/wiki-conventions.md`, `schema/wiki-layout.md`) is loaded by SessionStart hooks (`schema.sh`, one file per hook, each under the 10,000-character cap on hook context), not imported by a wiki's CLAUDE.md.

**Why.** The guards must apply only in wiki sessions, the clone must work wherever it lives on each machine, and Claude Code may run an installed copy of only the plugin folder.

**Consequences.** No fixed clone path anywhere. The repo itself is edited in sessions where the plugin is off, so the guards don't get in the way.

## 2. Source-neutral skills and pluggable sources
**Decision.** The skills, the guard, the settings template and `/wiki:init` know nothing about any particular source. A source has two levels:
- a **type**: its contract, `SOURCE.md`, with bash-parseable frontmatter (flat `key: value` lines and `- item` lists, no YAML or JSON library) and prose per operation for Claude;
- an **instance**: a key with parameters, one file per instance in the wiki's guard-protected `.claude/sources/instances/`; a wiki may have several instances of one type, and the key is `/wiki:ingest`'s argument.

Standard types live in wiki-tools (`plugins/wiki/sources/<type>/`); wiki-local types live in the wiki's protected `.claude/sources/types/` and may ship wrapper scripts. A local type may not shadow a standard one. Promotion of a local type to standard happens in a wiki-tools session, with fixtures and tests.

Every type is read-only by contract, plus narrowly declared bookkeeping writes, a mechanism local types may use (no standard type declares one since 23). The contract lists the allowed and forbidden tools; `/wiki:add-source` drafts the settings snippet. The operations are check, list new, fetch, optional mark ingested, cite and resolve citation; reading file formats is a shared core step. Each source declares the state it needs (at least `last_checked`), which the core stores generically in `raw/sync-log.md`. Platforms are declared per type and checked up front. A key with a `last_checked_<key>` line but no instance file is a manual key: its material enters through `raw/` or user statements.

The protected `.claude/sources/` tree is written only by the user: Claude drafts a file, and `install-source-file.sh`, run in a terminal outside Claude, checks it in a scratch copy, shows the diff, and installs it.

**Why.** New sources shouldn't need changes to the skills or the guard, and a wiki must be able to add a source of its own without a wiki-tools release.

**Consequences.** Anything specific to one source belongs in its `SOURCE.md`, never in a skill. A type whose read-only property can't be kept by tool permissions alone ships a wrapper with an allowlist of operations.

## 3. The guard: a guardrail that fails closed
**Decision.** One PreToolUse hook, `guard.py`, sees every tool call (matcher `*`). `hookjson.py` classifies each tool: shell (Bash, PowerShell, Monitor), write (Write, Edit, MultiEdit, NotebookEdit), read (Read, Grep, Glob), a list of harmless built-in tools that neither run commands nor write or read files, and `mcp__*` tools; any other name is refused, naming the tool. On every call that needs them it reads all standard and local contracts and the wiki's instances, and collects each type's `guard_words` and `scripts` and every filesystem instance's `roots`. It blocks `git push` (first, so no later exception can let one through); a shell command that starts a nested `claude` session (`claude` as a command word, not as text); commands naming the plugin's folder in any spelling, `.claude/sources`, `.claude/settings`, `.claude/plugins` (as a path segment), the wiki's `.claude/skills` (not the user's `~/.claude/skills`), `.claude/agents`, `.git/hooks`, `.git/config` or `.mcp.json`; a contract's guard word; and a filesystem root. Exceptions, Bash and Monitor only: a plain call of a core script or of a wrapper a contract lists, with no `; & | < > $`, backticks or `..`. Write tools may not touch the same protected paths (the whole plugin folder included) or anything inside a root (the path resolved first, `..` included), and non-Markdown content may not contain a guard word. For types with `agent_only: yes` (e.g. `codebase`), the main session's Read, Grep and Glob on the root are blocked, and its wrapper calls are limited to the contract's `main_ops`; subagents (hook input with `agent_id`) pass.

The guard fails closed: unparseable input blocks (for the tools it checks, any field it reads that isn't a string), as do an unknown tool, a shell call without a command and a write call without a path; and while any contract or instance can't be used, every shell and write call is refused except read-only diagnostics (`git status`/`log`/`diff`/`show`, `sources.sh list`/`show`/`contract`), with a message naming the file.

**The principle** (#24, Claude Code only). A protection goes into the wiki's Claude Code permission rules (`.claude/settings.json`, from `templates/project-settings.json` and `sources.sh settings`) when it can be expressed there reliably. A guard check is added only when it can't, and only when the harm it prevents justifies its maintenance cost. Irreversible harm (`git push`, writes into a source) stays guarded by a deterministic check even where a rule also covers it; checks fed by the source contracts (guard words, roots, agent_only) stay in the guard, since no rule knows them at hook time. The precedent: a contract's `forbidden_tools` for MCP tools become deny rules through `sources.sh settings`, with no guard check.

**Why.** The sources must stay read-only and the guard machinery protected from the session it guards. Matching command text can't be a security boundary, but it reliably stops accidental and straightforward misuse. Every kept check is one rules can't express (2026-11-18 review, #24): a committed rule can't name the per-machine plugin folder; `Bash(...)` rules match a command's shape and miss `git -C x push`, `env …` and `sh -c` (checked 2026-11-19: a `Bash(git push *)` deny rule let `eval "git push …"` through on Linux and Windows, and `Git push …` on Windows, `docs/guard.md`); rules don't see written content, apply to subagents alike (so not to agent_only) and are static, while contracts change at hook time. So `git push`, the broken-source fail-closed, protected paths and roots in shell and Write, guard words, the script exceptions and lookalikes, agent_only and the chained-call message all stay in the guard. No second-layer rules were added, so the wikis' settings didn't change.

The review's outcome: the protected words `hooks.json` and `disableAllHooks` were dropped (the plugin folder and `.claude/settings` already cover what they protected), and `claude plugin` became the nested-session check. New: every tool goes through the guard (Monitor's command was unchecked, NotebookEdit's writes too); Write tools refuse the whole plugin folder, as shell does (its skills, schema and templates are what every wiki session is told); files that run code later (`.git/hooks`, `.git/config`, `.mcp.json`, the wiki's `.claude/skills`, `.claude/agents`) are protected, but not the user's `~/.claude/skills`, where a source's reader may live (a session can therefore change the user's skills; accepted, as they are outside every wiki); `.claude/plugins` is matched as a segment; a write's path is resolved before the roots check. Deliberately left to Claude Code's permission prompt: `git config` and `git -c` (a key that runs commands, e.g. `core.hooksPath` or a `!` alias, is a long, growing list), and a Monitor WebSocket watch (`ws`, no command), which passes.

**Consequences.** Known false positives (a commit message containing "push", `git add .claude/...`, `cat .git/config` through Bash) are accepted and documented in `docs/guard.md`. Every tool call launches the guard (about 28 ms on Linux), and a new built-in tool is refused until it is classified in `hookjson.py`. A guard must never be weakened without saying so in the commit message.

## 4. Python behind bash launchers
**Decision.** The guard and the scripts' work are Python 3.11 or later, standard library only:
- **Hooks** run only through `py-launch.sh`, which fails closed: it finds Python (a cached path in a file named after the floor, `python-3.11`, else `python`, `python3`, `py -3`, rejecting the Windows Store alias and anything older than the floor), runs it as a child with `-I -S -X utf8`, and turns any exit other than 0 (allow) or 2 (block) into a block. Inside the script, everything sits in a `try` whose exceptions block. A script that imports a sibling adds its own folder to `sys.path` (`-I` removes it).
- **Scripts** keep their `.sh` names as launchers and run their module through `py-run.sh`: `sources.py`, `lint.py`, `wiki_check.py` (lint in-process), `sync_status.py`, `install_source.py`, `decode_download.py`, `file_snapshot.py`. Contract validation and settings parsing are `sourcelib.py` on top of `contract.py` (the guard's lean parser). A launcher keeps what touches the terminal or the shell: `install-source-file.sh` keeps the paste, the diff and the y/n prompt; `decode-download.sh` keeps its argument and path checks; `sync-status.sh` (a SessionStart hook) exits 0 on every path and reports a missing Python on stdout.
- **On Windows,** a Python started from Git Bash gets its arguments unconverted (`MSYS2_ARG_CONV_EXCL='*'` for that one command). Python refuses Git Bash mount paths (`/tmp`, …) rather than report them missing; callers pass them as `pwd -W` prints them. Messages show paths as they were given.
- **Bash stays** for the launchers, `py-launch.sh` and `py-run.sh` (they find Python), `lib-source.sh` (the wikis' local types use its helpers), `schema.sh`, `ocr.sh`, `local-folder/read.sh` (the model for local types, and it works on paths the user typed) and the `codebase` wrappers `git.sh` and `gh.sh`.

**Why.** On Windows every process start in Git Bash costs about 25 ms and a Python start 100–250 ms, so pipelines of `sed`, `awk` and `grep` made the guard and the scripts take seconds per call; one Python process does the same work in milliseconds. The names stay because contracts, settings and the guard name them. PowerShell would have meant a second implementation beside bash and platform-specific skills.

- **Repo tooling** follows the same rules outside the plugin: `scripts/pii_check.py` behind `scripts/pii-check.sh`, which finds Python through the plugin's `py-run.sh` (the wikis never run it).
- **Type checking** is mypy (`mypy.ini`; its major pinned as `mypy>=2,<3` in `pyproject.toml`'s `dev` group and locked in `uv.lock`, 19), a dev tool like ruff and pytest: CI's lint job and contributors run it; the plugin never imports or runs it, and the wikis never need it. Annotations cost nothing at run time: `from __future__ import annotations`, and in the guard's modules `typing` imported only under `TYPE_CHECKING` (importing it adds about 3 ms to every guard start; a test checks that the guard doesn't); elsewhere a plain `from typing import ...`. Strict, and the 3.11 floor: 20.

**Consequences.** No other Python without a decision recorded here. Python is a prerequisite for every wiki; `/wiki:init` checks for it.

## 5. Codebase research: `/wiki:research` and the `codebase` type
**Decision.** A `codebase` instance points at a local git clone (or a folder in it). It is a research type (`mode: research`): too large or fast-moving to ingest, so `/wiki:ingest` refuses it and sync-status leaves it out. `/wiki:research <key> "<question>" [--critique] [--worktree]` answers on demand:
- the main session reasons and never reads the code (enforced by `agent_only`); `wiki:source-researcher` agents act, at most 10 in parallel per step and at most 5 steps per run, then the session asks;
- agents read through `git.sh` (read-only operations at a pinned SHA of `ref`; the working tree only with `--worktree`) and `gh.sh` (PRs and issues, behind the instance's `gh_user`, never switching the active `gh` account); they may use the repo's own CLAUDE.md, skills and agents as knowledge, read-only;
- findings are merged into existing wiki pages where possible and cited verbatim with path, lines and SHA;
- critique is off by default; with `--critique`, an independent `wiki:critic` checks every claim through its own agents, for at most 3 rounds, then asks; pages are written only after acceptance;
- staleness is checked for cited code when the wiki answers from it (`drift`), not in sync-status;
- `git fetch` is allowed for agents; clone and worktree only after asking; no other writes to the clone. Shallow clones are accepted (no history before the boundary; `gh` gives older PR context).

**Why.** The code is too large for the main session's context and changes too fast to copy into the wiki; agents with capped, structured findings keep the main session's context small, and citations at a pinned SHA keep claims checkable.

**Consequences.** Run notes live per instance in `~/.cache/wiki-sources/<wiki>/<key>/runs/`, outside the repo, and notes on older SHAs are re-verified before reuse.

## 6. Research agents on Opus at medium effort; no code index
**Decision.** `source-researcher` runs on Opus at `medium` effort. `/wiki:research` uses no code index (graphify, SCIP, ctags, LSP and the like).

**Why.** Cheaper settings (Sonnet; Opus at low effort) gave thinner answers and some wrong ones. A cheaper setup must cost at least 15% less at unchanged quality. Exploration and search are too small a share of research time and cost for an index to reach the bar of 25% less time or cost at equal quality.

**Consequences.** If an index ever comes, it is a lead generator only: user-installed, built in the cache at a recorded SHA, never in the clone, and every claim re-read and cited at the pinned SHA. The names `setup.sh <key> graph` and the `git.sh` operations `graph-query`, `graph-path` and `graph-explain` are reserved for it.

## 7. Tests: pytest in two layers
**Decision.** The suite is pytest (`tests/test_*.py`, `tests/conftest.py`), started with `bash tests/run-tests.sh`, which runs it from the repo's `.venv` (19). pytest is a dev tool, pinned in `uv.lock`, never the plugin's; the launchers under test run the venv's Python (`pydata`), with `-I -S`, so through them the plugin still sees only the standard library. Two layers:
- **in-process:** a script's module is called through its `main(argv)`, the contract its launcher runs, with stdout and stderr captured in write order (`cli`, `guard_run`);
- **end to end:** the launchers and the bash scripts through a real bash (Git Bash on Windows).

`--e2e` runs the in-process tests through the launchers instead; it is required before a commit that touches a launcher or another `.sh` file. Tests never call a real source CLI or account; they use fakes (`tests/sources/<type>/`, e.g. a fake `gh`). Sections that build on one wiki step by step run as one ordered story and report each check as its own test. Recorded outputs (`tests/fixtures/*/*.out`) are compared byte for byte and rewritten with `--record`.

Windows paths get no special treatment: every test uses `tmp_path` with forward slashes, and one normaliser (`norm`) maps every spelling a path can come back in (native, forward slashes, `/c/...`, Git Bash's own mounts) to `@TMP@` and `@PLUGIN@`. On Windows, Git Bash started from native Python parses its own command line (globbing `*`, reading `@file`, mishandling `\"`), and Git's `bin/bash.exe` is a native launcher that parses it again and puts its own folders before a test's `PATH`. So arguments to bash go NUL-separated through a file, read by a fixed driver that execs `<git>/usr/bin/bash.exe`.

**Why.** Testing logic in-process makes the suite fast and free of shell quoting, while the end-to-end layer and `--e2e` keep the process boundary covered, which is where Windows differs.

**Consequences.** On Windows a restricted `PATH` still has Git's folders in front; a test can't assume bash sees only what it was given.

## 8. Changes through pull requests, checked on both platforms
**Decision.** `main` changes only through pull requests. CI (`.github/workflows/ci.yml`) runs lint (`bash scripts/dev-lint.sh`: `ruff check .`, `mypy`, `shellcheck -S warning` on every `*.sh`, no CRLF) and the suite, normally and with `--e2e`, on Linux and Windows; Claude reviews each pull request (`claude-review.yml`). Lint must also be clean before committing, through the same script. Line endings are LF everywhere (`.gitattributes`).

**Why.** Every script must run under Linux bash and Git Bash on Windows, and most Windows problems only show on Windows.

**Consequences.** Real use in a wiki on each machine is still checked by hand for changes that affect sessions.

## 9. Public from a fresh history, with a personal-data check
**Decision.** The public repo `draitchbar/wiki-tools` started from one commit of the cleaned files, not from the earlier history, which holds personal data (names, emails, addresses, hostnames) and stays private. Everything in the repo, commits included, is free of personal data: no real names, emails, places, hostnames, employer details, third parties or real wiki names, and commits carry only noreply emails and no `Claude-Session:` trailers. The rules are in `docs/development.md` ("Personal data") and `CONTRIBUTING.md`. MIT licence. Anyone can read, fork and install; issues and pull requests are for collaborators, who push branches to the repo, not to forks.

The check runs in three layers:
- `scripts/pii-check.sh` (stdlib Python behind `py-run.sh`): committed general patterns plus a private denylist (a local file, the secret `PII_DENYLIST` in CI), matched with folded case, Danish letter spellings, separators and encodings. A hit names its place and the entry's number, never the term.
- A committed pre-push hook (`.githooks/pre-push`), switched on per clone with `git config core.hooksPath .githooks`.
- CI: `pii.yml` on every PR event (a required check) and on push to `main`; an advisory section in `claude-review.yml` for what patterns miss.

The `main` ruleset requires a PR, the checks lint, tests on Linux and Windows, and pii; it allows squash merges only and blocks force pushes and deletion, with no bypass. Secret scanning and push protection are on.

**Why.** Rewriting history and flipping visibility leaves old commits reachable on GitHub, and a push to a public repo can't be taken back: pull request refs survive deleted branches and force pushes, and forks and clones keep everything. So the check runs before the push where it can, and CI catches the rest.

**Consequences.** Collaborators are trusted: the PII job and the review run with the secrets on a PR's own workflow code, so the owner reviews every change to `.github/workflows/` and the check. Edits in the GitHub web UI skip the hook. Issues and comments aren't scanned. A clone made before the release must never push here; every machine re-cloned.

## 10. Two coding agents, one set of rules
**Decision.** The repo is developed with Claude Code and with GitHub Copilot CLI, and every change must work in both (`CONTRIBUTING.md`). Rules and skills are written once. `CONTRIBUTING.md` holds the contribution rules for people and agents (workflow, personal data, push hook, identities, trailers); `AGENTS.md` imports it with `@CONTRIBUTING.md` and adds how to change the code and what only agents need; `CLAUDE.md` is the one line `@AGENTS.md`. Skills stay in `.claude/skills/`, which both agents read. No instruction or skill file only one agent reads, and no symlinks; `tests/test_agent_files.py` checks the layout. Enforcement stays where both agents meet it: the pre-push hook, CI and the review, with no agent hooks or committed permissions. Copilot's coding agent, `/delegate` and GitHub MCP write tools are not used, since they commit on GitHub past the hook (narrowed by 16 for sessions without `gh`); VS Code agent mode and Copilot code review are not set up.

**Why.** Collaborators may use either agent, and rules kept in two places drift. The `@` import is the one mechanism both agents document (Claude Code's docs recommend `@AGENTS.md` in `CLAUDE.md` and advise against a symlink on Windows, where `core.symlinks` is often off); both find skills in `.claude/skills/`. `CLAUDE.md` stays, although Claude Code 2.1.277 and later reads `AGENTS.md` on its own, because older or telemetry-off sessions read only `CLAUDE.md` and `claude-review.yml` names it. People follow links, agents follow imports, so each rule lives in the file of its main readers: `CONTRIBUTING.md` for policy, `AGENTS.md` for code and agent rules.

**Consequences.** Copilot reads `AGENTS.md` and `CLAUDE.md` both and so loads the rules twice; accepted (identical text, a few KB). Tested in Copilot CLI 1.0.112 (2026-11-15): its `Co-authored-by` trailer uses a GitHub noreply address and passes the personal-data check; `$ARGUMENTS` works; `argument-hint` isn't shown, so a skill names its arguments in `description`; `disable-model-invocation` was first found ignored; retested in 1.0.112 (2026-11-18), Copilot enforces it at its `skill` tool, for plugin and project skills, in every approval mode. A model can still read a refused skill's `SKILL.md` and follow it by hand (seen once, in autopilot with `--allow-all`), so a manual-only skill keeps a guard line telling the agent to stop unless the user typed the command. That line relies on the agent obeying it. The built-in GitHub MCP server is read-only by default. Copilot also reads hooks from `.claude/settings.json`, so a later guard hook for both agents could live in one file. Its hook behaviour is tested on Linux and Windows (the Copilot spike, `docs/development.md`, "Agents"): such a hook would need Claude's JSON deny reply rather than exit 2 alone (only the JSON reply's reason reaches the model) and a trusted folder (otherwise repo hooks are skipped); on Windows, Copilot runs hook commands in PowerShell and ignores `"shell": "bash"`, so the hook needs a `powershell` field that starts Git Bash by its path (1.0.113). A Copilot subagent's calls carry `agent_id`, which the guard uses to tell subagents from the main session.

## 11. Jira is tool-neutral
**Decision.** The standard `jira` type is `access: tools`, like `onenote` and `proton-files`: the contract lists the operations it needs (site access, find project, search, count, read issue, list comments, list remote links) and names no tools, allows none and denies none. The reader is chosen per wiki: `/wiki:add-source` settles with the user which tool does each operation and the allow and deny rules, and the instance's body records that mapping. The contract's Caveats list the readers seen working (the claude.ai "Atlassian MCP" connector; before it, the older "Atlassian" connector) as notes, not as rules.

**Why.** The type named the claude.ai Atlassian connector's tools, so when that connector was replaced (its endpoint is removed on 2027-03-01) every Jira wiki stopped until the contract changed. A different connector version, Atlassian's own server, a CLI or a skill would each have needed a new type. What the type defines (scopes, JQL, cursor, backfill, citations) doesn't depend on the tool; which tool reads Jira is a fact about the machine.

**Consequences.** `sources.sh settings jira` gives no rules; the user allows the reader's read tools and denies its write tools in settings, as for OneNote. Read-only rests on the connection's access, which Check reports, and on those deny rules. A dispatcher tool such as the Atlassian connector's `executeRead` reaches every Atlassian product read-only; allowing it is the user's choice, and only the contract's rule keeps it to the named operations. Type name, parameters, state and citations are unchanged, so wikis keep their pages and cursor; their instance file gains the reader's mapping in its body.

## 12. Reader binding is a skill
**Decision.** `/wiki:bind-reader <key>` binds an instance of a tool-neutral type to the reader on this machine. It runs in the main session and can be started by Claude: an ingest's Check starts it when the instance has no `## Reader` section or names a tool that's gone, and the ingest then stops until the user has installed the new instance file. The skill reads the contract's `## Bind` section (one small read-only test per operation, the fields to ask for, known dispatcher operation names). It has the user deny the reader's write tools and checks that they disappeared from the session's tools, then runs the tests on one item the user names as safe. It hands over the binding report, the instance file with its `## Reader` section, and the settings lines; it writes nothing itself. `check-settings` flags misspelled settings keys.

**Why.** Settling the reader in conversation, as `/wiki:add-source` did, left prose no script checked, and a new connector meant redoing it by hand (the Jira move, 2026-11-19). A plugin subagent was considered first. A review found that most open questions came from running in a subagent: no existing agent can reach MCP tools, a subagent can't ask the user, and its prompts surface from the background. The main session already sees and calls the tools and runs skill and CLI readers. A live run in a work wiki (2026-11-19, `tests/live/results.md`) settled the rest. A skill started by Claude inside `/wiki:ingest` ran without a prompt. Denied tools vanish from the session's tool list, so a deny rule can be verified. A misspelled top-level key in `.claude/settings.json` silently dropped every deny rule in it.

**Consequences.** Binding calls the source before the first ingest, after the instance is installed; `/wiki:add-source` still never calls it. Read-only during the tests rests on the deny rules the user adds first and on the user answering prompts with a plain "Yes" (a "don't ask again" saves a rule outside the install flow). The binding is machine-readable, so settings checks and the guard use it (13). `check-settings` flags only keys close to a known one, since Claude Code adds settings faster than a full list could follow.

## 13. The reader binding is machine-readable
**Decision.** A tool-neutral contract lists its operations in its frontmatter (`operations:`, `<name> (required|recommended|optional)`). An instance binds them in two frontmatter lists, drafted by `/wiki:bind-reader`: `reader`, one item per operation, `<operation>: <tool>`, where the tool is an MCP tool's name, optionally with one `<field>=<value>` limit on its input (a dispatcher's operation name), or a `Bash(...)` or `PowerShell(...)` permission rule; and `reader_deny`, the reader's write tools. The `## Reader` section in the body keeps the fixed arguments in words. Instance validation checks the binding against the contract's operations (known names, each bound once, every required one bound, no tool both limited and not, no denied tool bound). `sources.sh settings` and `check-settings` turn it into allow and deny rules, which may sit in the wiki's settings or the user's. Following the principle in 3, deny rules alone keep the `reader_deny` tools out, as they do a contract's `forbidden_tools`, and the guard checks only what no rule can express: it refuses a call to a tool bound only with limits unless one of their values is in its input; while a source file can't be used, it refuses the MCP tools any `reader` list names, since their limits are then unknown.

**Why.** Phase 2's binding was prose, which no script could check: the first live run (2026-11-19, `tests/live/results.md`) missed an allow line that only a manual re-read caught. Settings can't limit an MCP tool by its input, so a dispatcher such as the Atlassian connector's `executeRead`, which reaches every Atlassian product, was held to the contract's operations only by text. Phase 1 showed the hook payload carries the operation at `tool_input.name`. The limit guards reads, not writes: its value is keeping a session to the source (no other products, no people data), judged worth a check because no rule can do it. Denies were considered for the guard too, since Claude Code silently drops every rule in a settings file it ignores (a misspelled key, phase 1); that would be a second layer over rules that express them exactly, which 3 rules out, and `check-settings` now flags misspelled keys.

**Consequences.** The binding lives per instance, not per machine: instance files are what the guard trusts, and a wiki moved to another machine whose connector has other tool names is re-bound (Check finds the tools gone). An MCP tool is allowed once in settings, whatever its limits; the limits hold only through the guard, a guardrail: an MCP tool bound without a limit anywhere in the wiki is unlimited for every instance. The guard now reads every source file on each MCP call too. Only reader rules count from the user's settings; a contract's cache rules are per wiki and instance and still belong in the wiki's. Instances bound in prose only (phase 2) are re-bound at their next Check, through the skill's short path for a reader already described. Readers that run from an installed plugin's cache (`docs/roadmap.md`, parked) are not covered: the guard still refuses commands naming `.claude/plugins/`.

## 14. Unattended ingest defers its questions to a file
**Decision.** `/wiki:ingest <key> --unattended` and `/wiki:ingest all --unattended` never ask and never guess. A run starts only on a clean `wiki/`, `raw/sync-log.md` and `open-questions.md`. It refuses first ingests and **Check needed**, fails the source where attended would stop, and where a contract asks the user it takes the choice that fetches and writes nothing extra. What it would ask becomes a question in `open-questions.md` at the wiki root (`unclear`: the fact left out; `conflict`: both figures kept; `filing`: filed under the closest type, a model change only proposed), with a marker `^[open: <id>]` on each page. `/wiki:clarify` (manual-only) walks them with the user, who answers (cited as a user statement) or dismisses each, one commit and one `clarify` log entry per question. Any ingest closes a question its material settles; none applies a typed `answer:` line. `sourcelib.open_questions` parses the file for `sync_status.py` (count and oldest, at `startup|clear`) and `lint.py` (older than 30 days, markers and questions that don't match, a malformed file).

**Why.** A scheduled ingest is only useful if it can't stall on a question and can't write a guess into the wiki. One file to read in Obsidian, with markers where the facts belong, keeps what is missing visible on the pages and brings every answer back through the user. The format is fixed bullets so scripts can count and check it; the IDs avoid source names because commit messages carry them and the guard refuses those words.

**Consequences.** Scheduling itself (cron, `/loop`, `claude -p` permissions) is still the parked **Headless or `/loop` ingest** (`docs/roadmap.md`). The skills are prose: the behaviour is checked by a live run in a wiki, not by the suite. Contracts keep their own asks; the unattended rule for them is generic in the ingest skill. The sync status now also runs after `/clear`. An answer the user types into `open-questions.md` leaves it uncommitted, so scheduled runs refuse (naming `/wiki:clarify`) until it is applied.

## 15. Parallel tests: pytest-xdist by module, test modes as separate CI jobs
**Decision.** `tests/run-tests.sh` runs the modules in parallel with `-n auto --dist loadfile` when `pytest-xdist` is installed (it is in `uv.lock`, so always, except outside the lock with `WIKI_TOOLS_DEV_VENV=off`), and serially when it isn't or with `--check-names` (which prints at collection); arguments given after win, so `-n 0` runs serially. Like pytest it is a dev tool, pinned in `uv.lock` (19), never the plugin's. CI runs the two test modes (plain and `--e2e`) as separate matrix jobs, so each platform's modes run at the same time on separate runners.

**Why.** The Windows job took about 7.5 minutes (3:00 plain, 4:10 `--e2e`), against about one minute on Linux, and it sets the time every PR waits for. GitHub's runners for a public repo have 4 vCPUs, so more speed comes from more jobs as well as more workers. Most modules run one ordered story in a module-scoped fixture; xdist's default distribution spreads a module's tests over workers, each of which reruns the story (1.3× locally), while `loadfile` keeps a module on one worker (2.0× plain, 2.5× `--e2e` at 4 workers, Linux). The slowest story, then `test_codebase.py`, is ordered by design and bounded a run. Measured on CI (PR #20): the Windows jobs took 1:48 and 1:51, each test run about 1:30, against 7.5 minutes before.

**Consequences.** The required checks are `test (<os>, plain)` and `test (<os>, e2e)` for both platforms, four instead of two. Output from print debugging inside tests and `--pdb` need `-n 0`. A new slow story bounds the whole run. The codebase story did, at about 40 s locally on Windows; it is split into three modules (`test_codebase.py`, `test_codebase_fetch.py`, `test_codebase_grep.py`), each building its own repo (`tests/codebase_story.py`), so they run on separate workers. A module whose story grows past the others is the next to split.

## 16. Issues to pull requests by an agent: `/fix-issues-ai`
**Decision.** A manual-only repo skill, `/fix-issues-ai <numbers or titles>`, takes issues the user names and hands back pull requests for approval. The agent triages each issue (severity against the cost of maintenance: the complexity the fix adds, above all closer coupling between parts of the plugin, not tokens or time), closes what isn't worth fixing itself, with the reasons in a comment, puts an issue that needs a plan of its own on `docs/roadmap.md` (one pull request for the items, each referring to its issue, which stays open; the plan itself is not written), and decides a design question an issue leaves open, taking the option that changes less and weakens no guard and flagging it in the pull request. Each remaining issue gets one branch and one pull request, in Claude Code from parallel subagents in worktrees, each on a model the triage picks by the kind of work (a small one for mechanical doc fixes, the strongest for the guard, open choices and unknown causes), in Copilot CLI one after another on the session's model. The agent follows each pull request until CI is green, there is no conflict and the review's findings are answered, then stops; it never merges. Where a session has no `gh` (a Claude Code cloud session), GitHub MCP tools may open pull requests, comment and close issues; tools that write files, commits or branches, or merge, stay unused (this narrows decision 10's "no GitHub MCP write tools").

**Why.** Run by hand on four issues (2026-11-21): three pull requests merged without a review finding or a CI failure, one issue closed as not worth its risk. The user's time goes to the choices and the merge, so the skill decides and flags rather than asks: a wrong call costs one closed pull request or a reopened issue. One pull request per issue keeps each squash commit and each review about one thing. The MCP rule in decision 10 was about commits that pass the push hook; opening a pull request or closing an issue commits nothing, and a cloud session has no other way to do it.

**Consequences.** An issue can be closed without the user having seen the reasons first; they are in the comment, and the triage table is shown before anything is closed. Only the user starts the skill, and with no arguments it asks which issues. A subagent's worktree shares the clone's git config and runs the main checkout's copy of the push hook. A cloud session has no personal denylist, so its push hook checks the general patterns only; the `pii` job runs the same check. The skill is prose: it is checked by use, and `tests/test_agent_files.py` checks only its frontmatter and guard line.

## 17. The review writes a reviewer guide
**Decision.** Once a pull request has no blocking finding open, the Claude review (`claude-review.yml`) starts its summary comment with a reviewer guide for the person who approves, in sections, in this order: the goal (what the pull request achieves, in full sentences); a description (how it achieves it, in a few bullets that leave the reviewer understanding the pull request better than its file list); an assessment table of the blast radius (one of `none`, `contributors`, `one source`, `all wikis`, `guard`, `irreversible`, the highest that applies), the risk of a bug (low, medium or high by judgment, with what drove it and what was not assessed) and the cost of maintenance (low, medium or high, from coupling and new options or indirection, added or removed); the material or risky parts to focus on, each with what to check, left out when it would repeat the description; and a demo in at most three steps with made-up data ("refactor" and a sentence when no user can see the change). The guide covers the whole pull request, is derived from the diff, not from the description, and is written in fragments, except the goal. It is written on the first run with nothing blocking, and again only when a push changes one of its lines; otherwise the comment says it is unchanged, or withheld while a blocking finding is open. It holds no findings and no advice on merging. A pull request title or description that doesn't match the diff is a blocking finding, not a note in the guide, checked on every run against the whole pull request; the implementer fixes the text or answers, as for any finding (`docs/agent-pr-flow.md`). A small fixed set of emojis, named in the prompt, marks the risk and maintenance levels, the blast radius category, the status lines and each finding as blocking or not, and means nothing else; beyond those, the agent uses emojis at its discretion to make comments easier to read. Comments use plain Markdown (bold labels, bullets, code spans); the guide's sections and its assessment table are the only headings and table. The review agent may read and search the checkout (`Read`, `Grep`, `Glob`).

**Why.** Most pull requests are written by an agent and approved by one person, who needs to know where a few minutes of attention should go. Blast radius (who is hit if it is wrong) and risk (how likely it is wrong) are kept apart: a guard change that only rewords messages is wide and unlikely to break, and one merged level hides that. The categories are fixed so that a word means the same in every pull request; the rating and status emojis likewise. Other emojis are left to the agent's judgment, since the longer sectioned guide (below) reads better with them, as long as they can't be mistaken for a rating. A count of risk factors was tried on merged pull requests and rated message-only and test-only changes high, since most scripts here quote, match and handle paths; judgment with named reasons spread better in a trial on four merged pull requests (2026-11-21). The cost of maintenance means what it does in `/fix-issues-ai` (16), less the two kinds the blast radius and the risk already cover. A full guide on every run would repeat itself on each push. The first guides (2026-11-22) were too compact: a goal in fragments was hard to read even for the owner, and Focus named areas without saying what to check; the description says how the parts fit before the reviewer opens the diff, and a table lines up the three ratings. A wrong description blocks because the squash merge makes it the commit on `main`, and a reviewer shouldn't approve against it; withholding the guide until it is fixed says so.

**Consequences.** The guide is one agent's reading of the diff and can be wrong; a reviewer who reads only where it points will miss what it missed, which is why it says what it did not assess. Its demo is not run by the agent. The first guide reads the whole pull request, so that run costs more than a delta review. A pull request that changes `claude-review.yml` gets no review and no guide; a change to the guide's wording is tried locally (`claude -p` with the prompt, against merged pull requests, printing only) before it is merged.

## 19. Dev tools in a locked venv: `pyproject.toml`, `uv.lock`, `uv sync --locked`
**Decision.** The repo's dev tools (pytest, pytest-xdist, ruff, mypy 2.x, shellcheck-py) are the `dev` dependency group in `pyproject.toml` (a minimal `[project]` for the Python floor, `requires-python = ">=3.11"`, and `[tool.uv] package = false`: the repo is never built or installed). Every package, transitive ones included, is pinned with hashes in a committed `uv.lock`, one lock for every supported Python on Linux and Windows. They go into a gitignored `.venv` only by an explicit `uv sync --locked`, run by a person or a CI step; never `uv run`, which syncs implicitly. uv installs wheels only (`no-build = true`) and never downloads a Python (`python-downloads = "never"`; `dev-env.sh` and CI also set `UV_PYTHON_DOWNLOADS=never`, which would otherwise override the file). `tests/run-tests.sh` and `scripts/dev-lint.sh` use `.venv` without activation, through `scripts/dev-env.sh`, and stop when it is missing or out of date (`uv sync --locked --check`, offline); `WIKI_TOOLS_DEV_VENV=off` takes the tools from PATH instead, saying it runs outside the lock. CI installs uv with `astral-sh/setup-uv` pinned by commit SHA, its version equal to `required-version` (a test checks), with its bundled checksums required, and runs `uv sync --locked` on the Python `setup-python` gives. Lock bumps are a collaborator's pull request (`uv lock --upgrade`); no Dependabot. The plugin is unchanged: standard library only (4); `py-run.sh` and `py-launch.sh` are not touched.

**Why.** Reproducibility (the same tool versions on laptops, in CI and in agent sessions; an unpinned mypy or ruff could turn CI red on a release) and isolation (nothing in the user's or the system's Python, no `pip install --user`, no `--break-system-packages` under PEP 668). The standard layout: of eleven well-known Python projects checked on 2026-11-22, eight declare dev tools in `[dependency-groups]` (PEP 735) and six commit a `uv.lock`; none keeps a hashed `requirements-dev.txt`, the earlier draft's design, and pip's support for the standard lock file (PEP 751) is still experimental. uv runs on Windows and in Actions, so one lock and one install path serve every job. The security review (`docs/kfchou-security-review.md`, finding 3) objected to a git hook running `uv run` on every commit, which installs whatever a changed script declares; an explicit `uv sync --locked` from a committed, hashed lock does not, so the rule is "never `uv run`", not "never uv". Without `no-build` uv would run a package's build code where no wheel fits (every package in the lock has an sdist); wheels cover CPython 3.11 to 3.15 on Linux and Windows. A stale venv only warned about would give "green locally, red in CI" under hundreds of pytest lines, so the scripts stop instead.

**Consequences.** uv 0.13.7 or later is a prerequisite for developing the repo (not for the wikis), installed by the user; a session without it, a Claude Code cloud session among them, installs it or runs with `WIKI_TOOLS_DEV_VENV=off` and reports that the run was outside the lock. `uv sync --locked` once per clone and per worktree, again after a pull that changes `uv.lock`. Tool versions move only by a pull request that changes `uv.lock`. The repository's settings have Dependabot alerts on and "Dependabot security updates" (automatic pull requests, which need no config) off: such a pull request gets no repository secrets, so the required `pii` check fails, and its release notes would carry third parties' names into `main`'s history. In a Windows venv `sys.executable` is `.venv\Scripts\python.exe`, a launcher that starts the base Python, and the plugin under test runs through it.

## 20. Type checking: mypy, strict, and a 3.11 floor
**Decision.** Every module behind a launcher (4: the twelve in `plugins/wiki/scripts/`) and `scripts/pii_check.py` pass `mypy --strict` (`mypy.ini`: `strict = True`, no relaxed module), and ruff's `ANN` rules, `ANN401` included, keep every function annotated (`ruff.toml`). mypy is a dev tool (4, 19), pinned `mypy>=2,<3`; CI's lint job and `scripts/dev-lint.sh` run it. The Python floor is 3.11: the launchers' interpreter cache is named after it (`python-3.11`), so a cache from an older floor is never read, and `guard.py` checks the version first and blocks with "Python 3.11 or later is needed" (it parses on an old Python up to that check); CI runs the tests on 3.13 only: mypy and ruff check against 3.11, and a test job on the floor waits until it is needed (`docs/roadmap.md`, Parked). At run time: `from __future__ import annotations` in every module; in the guard's modules (`guard.py`, `contract.py`, `hookjson.py`) `typing` only under `TYPE_CHECKING = False` / `if TYPE_CHECKING:`, and a test checks that importing the guard leaves `typing` out; elsewhere a plain `from typing import ...` (`cast`, `@overload`, a `NamedTuple` base). `tests/` is out of scope (ruff ignores `ANN` there; mypy doesn't list it).

**Why.** Wrong shapes shipped unseen: `None` reaching a string method, a `bytes | str` return used as `str`, attributes a class didn't declare. mypy is the owner's choice and the most used checker; the annotations need only the standard library's `typing`. Strict because a checker that skips unannotated code checks little, and ruff `ANN` with it because the two check different things: `ANN` that annotations exist, mypy that they are right. mypy 2 no longer targets 3.9, and 3.10 reached its end of life in October 2026, so a 3.10 floor would soon need raising again; 3.11's `typing` has `NotRequired`, `Self` and `assert_never`. The launchers trusted a cached interpreter without probing it, so without the renamed cache a machine on 3.10 would have blocked every tool call with only "guard.py failed". Importing `typing` adds about 3 ms to each guard start (about 12 %), paid on every tool call; annotations under `__future__` cost nothing measurable. The modules were made strict one PR at a time (#64, #71, #72), the guard's parser first, from a spike's baseline (66 errors at `check_untyped_defs`, none of them a bug).

**Consequences.** Users on a Python older than 3.11 (Ubuntu 22.04's system Python) get a blocking guard, with a message saying what to install, until they upgrade. A new module in scope goes into `mypy.ini`'s `files` and is strict from its first line. An explicit `Any` stays at the JSON boundary, with its reason; none is in use. A change to annotations only needs no new test (AGENTS.md); one that changes behaviour does. Typing `tests/` is parked (`docs/roadmap.md`). `claude-review.yml`'s prompt still says "Python 3.9+": it needs a one-line pull request of its own, since the review skips a pull request that changes that file.

## 21. Features to a pull request by an agent: `/implement-feature-ai`
**Decision.** A manual-only repo skill, `/implement-feature-ai <goal>`, takes a goal (a description or a `docs/roadmap.md` item) and hands back one pull request for approval. The agent settles the goal's open choices and writes a spec file every subagent reads. It asks the user, one question at a time with its recommendation, only what it can't settle with confidence (from what the user said, the repo's decisions and precedent, or a fact it looks up) and what would be hard to revert after the merge (existing wikis, a guardrail, data and trust, an interface others depend on, a lasting cost); every other choice it decides, with its reason, in the spec and the pull request's decisions, for the user to overrule. The design-session decision is the agent's too. When the goal needs a design (a new ADR, mechanism, contract key, skill, source type or dependency, a tech stack, a migration, the guard, or real trade-offs), a research subagent drafts it with cited sources, a reviewer on the strongest model reviews it, and a design pull request with `docs/plans/<slug>.md` stops the run until the owner merges it; otherwise a planner subagent writes the plan outside the repo and the run goes on. Each task is built by its own subagent on its own branch, `<agent>/<slug>-<task>` beside the integration branch `<agent>/<slug>` (in Claude Code in parallel worktrees, at most 4 locally and 10 in a cloud session; in Copilot CLI one after another), reviewed by a fresh-context reviewer at least as strong as the implementer (in Copilot CLI, rubber duck, a different model family), and merged without squashing into the integration branch, the only one pushed locally. A full test run and one review of the whole diff come before the pull request, whose description is the squash commit and so names no model; the models used are reported in the hand-over. The run is resumable from the pull requests and branches it left. The model table, the implementer brief, the pull request text and following a pull request are shared with `/fix-issues-ai` (16) in `docs/agent-pr-flow.md`.

**Why.** Features need decisions issues don't settle, so the user's time goes to the few choices only they can make and to the merge, and the design, where one is needed, is merged before code is written. Fresh-context reviewers see what the implementer missed; one pull request per goal keeps the squash commit about one thing, while the task commits stay on the branch for review. Parallel subagents cost many times the tokens, so they are capped.

**Consequences.** A goal with a design takes two runs and two merges. The skill is prose, checked by use; `tests/test_agent_files.py` checks only its frontmatter and guard line. Copilot CLI can't set a subagent's model from a skill, so the model is named in the brief and Copilot chooses. The first run (2026-11-22) asked about every choice, one by one, and so stopped far more than it needed to; the user asked for questions only where the agent is unsure and the answer is hard to revert. A choice the agent gets wrong is then caught at review, which costs a fix, not a migration.

Existing wikis rebind once and drop the `create_label` and `label_thread` allows (`docs/sources.md`). A `gws` reader is then a new binding, not a new contract.

## 24. Functional style where it fits
**Decision.** In Python, a value built from an iterable with no side effects is a comprehension, a generator expression or `any`/`all`. A loop stays when its body does I/O, carries state between items, reports several different errors, or would need a nested or multi-condition comprehension. No fluent or chaining wrapper. Bash stays builtin-first. ruff enforces the simple cases (`C4`, `PERF401`); `C408` is off, since `dict(a=1)` is fine. The guard's modules (`guard.py`, `contract.py`, `hookjson.py`) are exempt from `PERF401` and aren't rewritten for style alone.

**Why.** A survey of the non-test Python (2026-11-23) found 149 `for` loops, of which only about 6 to 11% were plain maps or filters; the rest mostly validate in order, track state, exit early or do I/O, and read better as loops. Python has no chainable collection API, and the standard-library-only rule (4) excludes libraries that add one. The guard fails closed, so a change in evaluation order or laziness can wrongly block or allow a call. In bash, each pipeline stage is a process (about 25 ms in Git Bash, 4), no script sets `pipefail`, so a failed stage goes unnoticed, and a piped `while` loses its variables.

**Consequences.** New code follows the rule and ruff catches the plain cases. Existing loops outside the guard were converted only where ruff flagged them. Which loops count as stateful stays a judgement for the author and the reviewer.
