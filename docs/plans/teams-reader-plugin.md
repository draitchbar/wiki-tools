# Spike: a Teams reader plugin for `ms-teams`

Status: cut down 2026-11-28. **The folder snapshot stays in the core**, and so does the folder walk. The plugin carries no code. The first version (#122) moved the snapshot too, which made the spike depend on two hard gates: a launcher that finds a compatible `wiki` across layouts, and a guard exception that trusts a reader root to run scripts. Both exist only to move one script that is generic already: `file-snapshot.sh` serves any `access: tools` reader whose list folder has no modified times (`docs/adr.md`, 10). Those gates wait for the first reader plugin that brings real code (`gws`, a OneNote base reader), where they have to be solved anyway (**Later: readers with code**).

The Teams half of the roadmap item **Reader plugins for connector workarounds**: move what is specific to reading Teams with the claude.ai Microsoft 365 connector (its operation mapping, denies, settings lines and quirks) out of the core `wiki` plugin into a second plugin, `teams-reader`, in the wiki-tools marketplace. It serves only the `ms-teams` source type. This page plans a spike that answers whether a prose-only reader plugin works and with what shape. It builds nothing that is merged, and no-go is an acceptable outcome. The Atlassian half (the dispatcher limit, `docs/adr.md`, 11) and readers from other marketplaces (**Readers from installed plugins**) stay parked.

## Before the spike: the binding field for auxiliary rules

This is a change of its own, built and merged before the spike because it pays off without any plugin. Today the snapshot allow `Bash(bash */scripts/file-snapshot.sh *)` is a hand-written settings line in the contract's `## Bind`, which `check-settings` can't verify (contract Caveats). OneNote's reader rules are similar: the user writes them by hand, and nothing checks them.

- A validated binding field in the instance (beside `reader` and `reader_deny`) for rules a binding needs beyond its operations: the snapshot allow for a Teams instance with folders and no modified times; a reader's own rules for `onenote`.
- `sources.sh settings --key` emits it, `check-settings` verifies it (and says whether a rule found only in user settings is enough: locally yes, for a cloud routine no, it must be in the wiki's committed settings), and `stale_rules` reports it once the last binding using it is gone. Today the old snapshot allow is deliberately not reported (`tests/test_sources.py`, ~227–240).
- `reader` keeps only operation bindings; the contract's `read_tools` keeps applying by type, also to unbound instances.
- Tests: no binding, a missing rule, the last binding removed, a rule only in user settings.
- Its own ADR amendment (11) and migration line for bound Teams instances.

The spike assumes this field exists.

## Principles

- **One repo, separate plugins.** Every reader plugin lives in this repo, under `plugins/<type>-reader/`, and is listed in this repo's marketplace (`.claude-plugin/marketplace.json`) beside `wiki`. Each is installed on its own, per wiki: `claude plugin install <type>-reader@wiki-tools --scope project`. They share the repo's CI, lint, tests, personal-data check and review.
- **One-way dependency.** `teams-reader` may use `wiki` (its contract, its scripts, its skills); no code, skill or contract in `wiki` names `teams-reader`. `wiki` alone keeps working, and ADR 1 still holds for it. The repo's user docs link to `teams-reader`'s README (check 9); a link is documentation, not a dependency.
- **Prose only.** `teams-reader` holds notes for the model (a skill, or a few) and its README; no scripts, no hooks, no Python. Anything that must run stays in the core, as a generic mechanism.
- **Parity, not stricter or looser.** Every protection, allow and deny rule a bound Teams instance has today it still has; nothing new is enforced (no URI limit on `read_resource`). The one guard change (check 2) only adds refusals.
- **Settings first, the guard where it is today** (`docs/adr.md`, 3). Allow and deny stay settings rules, generated by `sources.sh settings` and verified by `check-settings`. The snapshot keeps its place in `CORE_SCRIPTS` and its plain-call checks unchanged.
- **Only where Teams is added.** Locally, `teams-reader` is enabled in a wiki's `enabledPlugins` only when that wiki has an `ms-teams` instance, and ships no settings. In the cloud, `enabledPlugins` doesn't apply (check 7).
- **The core stays generic.** The core names no Teams tool, server or plugin (`tests/test_source_neutral.py`). Its remaining Teams parts are data and policy: the tool-neutral contract, its List new policy (the walk, the snapshot's compare and save), and the cloud-name pair.

## Spike checks

Each check records what was run, on which platform and Claude Code version, and the result, in **Findings**. Live checks use a throwaway wiki and a test folder with made-up content; nothing personal goes into this page. The prototype lives on a spike branch and is not merged. Layouts: the clone, the installed copy (`~/.claude/plugins/cache/…`, where the two plugins may sit at different versions) and the cloud clone.

1. **Two plugins, enabled per wiki.** Enable `wiki` and `teams-reader` in a test wiki's `.claude/settings.json`; both load, and the notes skill shows in the session's skill list. A wiki without `teams-reader` loads `wiki` alone; a Teams instance there fails clearly at Check (the contract's neutral message: "no reader notes for this instance; see its `## Reader`"), not silently.
2. **The notes are protected in every layout.** In the clone and cloud layouts the guard protects the whole clone, so `plugins/teams-reader/` is covered already; show it with fixtures. In the installed cache the guard protects only `wiki`'s own folder, so a sibling `teams-reader` folder is open to shell and Write. Today the same notes sit inside the protected `wiki` folder, so for parity the guard must also protect its marketplace's plugin folders in the cache, derived from the guard's own path (never from wiki data). Settle the cache layout (`cache/<marketplace>/<plugin>/<version>/`?) on Linux and Windows. This only adds refusals and exempts nothing, so it doesn't loosen the guard. Fixtures: shell and Write on a sibling plugin refused in Git Bash and Windows path forms; another marketplace's plugin and the user's `~/.claude/skills` untouched.
3. **Binding finds the notes.** `/wiki:bind-reader` reads the contract's `## Bind` today. The contract's `## Bind` says, generically, to load the skill whose description says it holds reader notes for this type, if one is loaded, and to follow its mapping, denies and rules. The binding it produces (`reader`, `reader_deny`, the binding field, `## Reader` with a line naming the notes skill) matches today's rules exactly. Also check what happens with two such skills, and with none: then bind-reader works as for an unknown reader, testing each operation from the contract's steps, as today.
4. **The notes in an ingest.** The instance's `## Reader` names the notes skill. `/wiki:ingest` loads it at Check with no prompt and follows its quirks (chat paging, reply truncation, the folder paging) through List new and Fetch. Check whether a plugin skill needs a permission rule (`Skill(...)`) and whether `wiki:ingest`'s `allowed-tools` would have to name it (it may not, by the one-way rule; then the rule goes into the binding field). Repeat it unattended (`/wiki:ingest all --unattended`), where nothing may prompt.
5. **Version skew** (installed layout only; the clone and the cloud clone keep both plugins at one commit). With `teams-reader` older or newer than `wiki`, what breaks: an operation the contract renamed, a binding field the core doesn't know. Decide whether the notes declare the contract version they were written for and Check compares it, or whether skew is documented only.
6. **Copilot CLI** (desk check only; Teams in Copilot is parked). Whether Copilot loads a second plugin and its skills; a follow-up, not a go criterion.
7. **Cloud.** The cloud ignores a wiki's `enabledPlugins`, so loading `teams-reader` loads it for every wiki in that environment: add it only in environments whose wikis have a Teams instance, and find whether `CLAUDE_CODE_PLUGIN_DIRS` takes two folders (separator, order). Both come from the one clone `cloud-update.sh` keeps current (ADR 19). A cloud routine on a bound Teams wiki loads the notes, shows the cloud-name denies in effect and runs the walk and snapshot with no prompt (the cloud connector baseline is itself still pending live checks, `cloud/SETUP.md`).
8. **Migration.** An existing bound instance keeps its `reader`, `reader_deny`, `files.tsv` and settings; it gains the notes line in `## Reader`, added by `/wiki:bind-reader` or a named manual step. Without `teams-reader` enabled, Check says so. Nothing about the snapshot changes.
9. **Repo plumbing and docs.** The marketplace lists both plugins; `tests/test_agent_files.py` is extended to plugin skills (it scans only `.claude/skills` today); a new test checks that nothing under `plugins/wiki/` names `teams-reader` (`test_source_neutral.py` doesn't scan contracts for it). A draft `plugins/teams-reader/README.md` holds the whole enabling flow, so a user needs no other page:
    1. Add the source: `/wiki:add-source` for `ms-teams` (the user's step).
    2. Enable the reader in that wiki only: `claude plugin install teams-reader@wiki-tools --scope project` (from a clone: `claude plugin enable … --scope project`), then restart `claude`; it writes `enabledPlugins` in the wiki's `.claude/settings.json`.
    3. Bind: `/wiki:bind-reader <key>`, which writes `reader`, `reader_deny`, the binding field and `## Reader`.
    4. Settings: `sources.sh settings ms-teams --key <key>`, installed in the wiki's settings (committed, for a cloud routine); `check-settings` confirms.
    5. Ingest: `/wiki:ingest` (the user's step); without the plugin, Check stops with its message.
    6. Remove: delete the instance, remove the rules `check-settings` reports as stale, `claude plugin disable teams-reader@wiki-tools --scope project`.
    7. Cloud: add `teams-reader` to the environment's `CLAUDE_CODE_PLUGIN_DIRS`, only for environments whose wikis use Teams.
    8. Migration from a wiki bound before the move.

    Links to it from `README.md` (its source-type list), `docs/setup.md` (its Microsoft Teams entry) and `docs/sources.md`. The README's steps are the ones the live tests follow, so a run checks the docs too.

## E2E tests

**Automated, in CI** (`bash tests/run-tests.sh --e2e`, Linux and Windows; fakes only, as for every repo test):
- the guard through `py-launch.sh`: shell and Write on `teams-reader`'s files refused in the clone layout and an installed-cache layout; the snapshot's existing fixtures unchanged (check 2);
- `sources.sh settings ms-teams --key` and `check-settings` on an instance bound through the notes: the same rules as today (check 3);
- a wiki without `teams-reader`: `wiki` alone passes its tests, and a Teams instance's Check fails with its message (check 1);
- migration: an instance and settings from before the move, with the notes line added, give the same settings and compare result (check 8).

**Live, in real wikis** (by hand, before go; not in CI). Real Claude Code sessions with the real guard, in throwaway wikis set up by following the README draft, against a test team and SharePoint folder with made-up content and the claude.ai Microsoft 365 connector. Linux in the disposable container (`tests/live/`, with a `teams-reader` lane; whether the connector signs in there is itself a check) and Windows (Git Bash) on a developer machine:
- **W1, Teams wiki:** README steps 1–5; the first ingest loads the notes, walks, snapshots and writes pages with no prompt beyond the user's steps; a second ingest after a file is added, changed and removed reports exactly those.
- **W2, a wiki without Teams** on the same machine: `teams-reader` doesn't load, no Teams rules in its settings, `/wiki:init`'s check (`wiki-check.sh`) clean.
- **W3, protection:** in W1, prompts that try an Edit of a `teams-reader` file and a shell write to it; the guard refuses each, in the installed layout too.
- **W4, removal:** step 6 in W1; `check-settings` reports the stale rules, and after the disable the plugin no longer loads.
- **W5, migration:** a wiki bound with today's `wiki`, moved by step 8; the next ingest matches.
- **W6, cloud:** a cloud routine on W1's committed settings (check 7).

Steps that start a manual-only skill (`/wiki:add-source`, `/wiki:ingest`, `/wiki:init`) are the user's; Claude runs `/wiki:bind-reader`, `sources.sh`, `check-settings` and `wiki-check.sh`. Each run adds a line to a results file like `tests/live/results.md` (Claude Code version, platform, case, outcome); session IDs, tenant and folder names, and other personal data stay out of it.

## What the spike decides

- **Go** if checks 1–4, 7, 8 and 9 pass (check 2 in every layout on Linux and Windows, check 7 with a Teams-only cloud routine), check 5 has a decision, the automated e2e tests are green in CI and the live cases W1–W6 pass on both platforms (W6 on Linux). **No-go** otherwise: the notes stay in the contract and the Teams part of the roadmap item closes.
- For a go: the layout, how bind-reader and ingest find the notes (checks 3, 4), the guard's protection of sibling plugins (check 2), the skew rule (check 5), the cloud setup (check 7), and a build plan (a revision of this page) with its tests (the e2e tests above kept, the live cases as a release check). ADR amendments: 1 (a second plugin), 2 and 10 (reader notes live in a reader plugin; the snapshot stays a core mechanism, no longer a candidate to move), 3 (the guard protects its marketplace's plugin folders), 20 (a second folder in `CLAUDE_CODE_PLUGIN_DIRS`). Then the docs to update.

## Pattern for the other sources

The spike is meant as the pattern for moving other readers' notes out of the core. A go here doesn't move them; each would be its own plan.

**Two layers.** Every tool reader is a base reader plus a wiki reader plugin:
1. **Base reader:** generic, knows nothing of wikis, usable in any session, and owns its sign-in and scope. A claude.ai connector (Teams, Gmail, Drive, Jira), another marketplace's plugin (`proton`), or the user's own skill or CLI under `~/.claude/skills` (OneNote). It is not shipped here and stays the user's.
2. **Wiki reader plugin** (`<type>-reader`, this marketplace): the adapter's notes. It maps the contract's operations to the base reader's tools or commands, with fixed arguments, denies, auxiliary rules and quirks. It depends one way on `wiki` and on the base reader's **interface**, never on its code; its README documents that interface, so any base reader that meets it can be bound.

| Type | Plugin | What would move | Needs beyond this spike |
|---|---|---|---|
| `gmail` | `gmail-reader` | `## Bind` mapping, fixed arguments, denies, connector quirks | nothing; the simplest second case |
| `google-drive` | `google-drive-reader` | mapping, denies, quirks (`decode-download.sh` stays core) | nothing; its cloud name is still unknown (`connectors.md`), so it can't run in the cloud either way |
| `jira` | `jira-reader` | mapping, `executeRead` arguments, denies, quirks | to use the dispatcher operations in the cloud, a generic way to hold the `field=value` limit under the cloud name (today denied there, which is parity); a hook in the plugin would be code (**Later**) |
| `proton-files` | `proton-files-reader` | Proton-specific commands, arguments, quirks | the external `proton` plugin is its base reader and stays the user's install; its allow, hand-written in user settings today, goes into the binding field |
| `onenote` | `onenote-reader` | the operation mapping and Bind tests against a defined base-reader interface (`notebooks`, `sections`, `pages`, `page`, `files`, GET only), the scope check, Graph quirks | a base reader meeting that interface; its rules move into the binding field (**Before the spike**). A token-taking script shipped here (`docs/plans/onenote-cloud.md`) would be code (**Later**) |
| `codebase`, `local-folder` | none | stay core | — |

`codebase` and `local-folder` are `access: filesystem` types: their wrappers are the source's read-only access, not a separate reader, and `codebase`'s `agent_only` and root checks are core guard checks. They stay in the core.

## Later: readers with code

A reader plugin that ships scripts or a hook (a `gws` wrapper, a OneNote reader script, an Atlassian dispatcher hook) needs what this spike leaves out. Its own plan takes these on, and moving the snapshot can be reconsidered then:
- **A launcher across layouts:** the plugin's Python must find a compatible `wiki` root (for `contract`, `sourcelib`) with no fixed path, under `-I` and without `.venv`, and fail clearly when `wiki` is missing or at another version. It also needs an amendment to ADR 4 for Python outside `plugins/wiki/`.
- **A guard exception for a trusted reader root:** a script under a sibling plugin the guard trusts, with today's plain-call checks (lookalikes, chained and redirected calls, `..`, PowerShell). The root is trusted from the guard's own location, never from wiki data. Check 2's protection of sibling plugins is the first half of this.

## Out of scope

Moving the snapshot or the walk; new enforcement (no URI limit on `read_resource`); a guard, hook or script in `teams-reader`; other Microsoft 365 sources (Outlook, OneNote); the Atlassian dispatcher limit; readers from other marketplaces; pruning the walk by folder size (#82); a Graph reader; keeping the snapshot across cloud VMs; Teams in Copilot.
