# Spike: a Teams reader plugin for `ms-teams`

Status: cut down 2026-11-28. **The folder snapshot stays in the core**, and so does the folder walk. The plugin carries no code. The first version (#122) moved the snapshot too, which made the spike depend on two hard gates: a launcher that finds a compatible `wiki` across layouts, and a guard exception that trusts a reader root to run scripts. Both exist only to move one script that is generic already: `file-snapshot.sh` serves any `access: tools` reader whose list folder has no modified times (`docs/adr.md`, 10). Those gates wait for the first reader plugin that brings real code (`gws`, a OneNote base reader), where they have to be solved anyway (**Later: readers with code**). Reviewed 2026-11-28 (one round, folded in): the guard already protects the reader's folder in every layout, so this spike changes nothing in the guard; finding a reader at hook time waits for the first reader with guard fields. Decided 2026-11-28: no semver for `wiki`; the manifest's `interface` handles skew in the installed copy (**The injection interface**, check 5), so nothing needs settling before the spike.

The Teams half of the roadmap item **Reader plugins for connector workarounds**: move what is specific to reading Teams with the claude.ai Microsoft 365 connector (its operation mapping, denies, settings lines and quirks) out of the core `wiki` plugin into a second plugin, `teams-reader`, in the wiki-tools marketplace. It serves only the `ms-teams` source type. This page plans a spike that answers whether a prose-only reader plugin works and with what shape. It builds nothing that is merged, and no-go is an acceptable outcome. The Atlassian half (the dispatcher limit, `docs/adr.md`, 11) and readers from other marketplaces (**Readers from installed plugins**) stay parked.

## Before the spike: done

The binding field for auxiliary rules is built: the instance list `reader_allow` (`docs/adr.md`, 11). It holds the snapshot allow and a reader's helper-script and cache rules in named shapes only (`Skill(...)` not yet; add it if check 4 needs one), `sources.sh settings` (the whole wiki, or `<type> --key <key>`) emits it, `check-settings` verifies it and `stale` reports a helper-script allow no binding needs. `reader` keeps only operation bindings.

The spike assumes this field exists.

## Principles

- **One repo, separate plugins.** Every reader plugin lives in this repo, under `plugins/<type>-reader/`, and is listed in this repo's marketplace (`.claude-plugin/marketplace.json`) beside `wiki`. Each is installed on its own, per wiki: `claude plugin install <type>-reader@wiki-tools --scope project`. They share the repo's CI, lint, tests, personal-data check and review.
- **One-way dependency.** `teams-reader` may use `wiki` (its contract, its scripts, its skills); no code, skill or contract in `wiki` names `teams-reader`. `wiki` alone keeps working; ADR 1 (one plugin, everything under `plugins/wiki/`) is amended for a second plugin, and holds for `wiki` otherwise. The repo's user docs link to `teams-reader`'s README (check 9); a link is documentation, not a dependency.
- **Prose and data only.** `teams-reader` holds notes for the model (a skill, or a few), its manifest (**The injection interface**) and its README; no scripts, no Python, no hooks. Anything that must run stays in the core, as a generic mechanism.
- **Injection, not code.** A reader adds to the guard and the settings only as data in a format the core defines and enforces (**The injection interface**); the core names no reader. A reader's own guard hook is rejected (same section, **Why not a reader hook**).
- **Parity, not stricter or looser.** Every protection, allow and deny rule a bound Teams instance has today it still has; nothing new is enforced (no URI limit on `read_resource`). The guard doesn't change: it protects the reader's folder already (check 1). A missing reader stops its instance at Check, not the guard (check 2).
- **Settings first, the guard where it is today** (`docs/adr.md`, 3). Allow and deny stay settings rules, generated by `sources.sh settings` and verified by `check-settings`. The snapshot keeps its place in `CORE_SCRIPTS` and its plain-call checks unchanged.
- **Only where Teams is added.** Locally, `teams-reader` is enabled in a wiki's `enabledPlugins` only when that wiki has an `ms-teams` instance, and ships no settings. In the cloud, `enabledPlugins` doesn't apply (check 7).
- **The core stays generic.** The core names no Teams tool, server or plugin (`tests/test_source_neutral.py`). Its remaining Teams parts are data and policy: the tool-neutral contract, its List new policy (the walk, the snapshot's compare and save), and the cloud-name pair.

## The injection interface

How a reader adds its rules to the guard and the settings while depending only on `wiki`, never the reverse. Researched 2026-11-28 from the code and the Claude Code documentation (hooks, plugins reference, plugin loading and dependencies, permissions); the facts marked **(docs)** come from those pages, nothing here was run.

**What Claude Code offers** (docs):
- All PreToolUse hooks matching a call run in parallel, and their decisions combine as deny > ask > allow: a second hook can add refusals but never let through a call another hook refuses. A command hook that times out doesn't block unless it sets `onFailure: "block"`.
- A plugin can't ship permission rules: no plugin `settings.json` for permissions, no manifest key.
- `plugin.json` has `dependencies`, with semver ranges (`{name, marketplace, version}`): a missing dependency is installed, and the dependent plugin is disabled while its dependency is disabled or out of range.
- A hook gets its own plugin's `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA`, nothing about other plugins. Installed plugins sit at `cache/<marketplace>/<plugin>/<version>/`, several versions side by side; the active one is recorded in `installed_plugins.json`, which the loading page describes but doesn't offer as an interface.

**The shape: dependency inversion through data.** The guard already works so for source types: it names no source and enforces guard words, allowed scripts, roots and dispatcher limits that contracts and instances declare. A reader does the same through a manifest at its plugin root (say `READER.md`, frontmatter in the contracts' flat format), in fields the core defines:

| Field | Kind | Used by |
|---|---|---|
| `serves: <type>`, `interface: <n>` | which source type; the version of the core's reader format | Check, `/wiki:bind-reader` |
| the operation mapping, fixed arguments, the denies the type always needs | binding notes | `/wiki:bind-reader`, which finds them by plugin name (check 3), never by a skill's description |
| `reader_deny`, auxiliary rules | settings | copied into the instance at bind time; then `sources.sh settings` and `check-settings`, as today |
| `guard_words`, `protected` | restrictions | the core guard, as for contracts |
| `scripts` | exceptions: plain calls of scripts under the reader's folder | the core guard, with today's plain-call and lookalike checks (**Later**) |
| dispatcher limits (`field=value`) | restrictions | the core guard (data in `reader` already) |

The reader declares `dependencies: [{name: wiki, marketplace: wiki-tools}]`, with no version range, so Claude Code installs and enables `wiki` with it, and the manifest's `interface` lets Check refuse a reader written for another format. **No semver for `wiki`** (decided 2026-11-28): both plugins live in this repo, so the clone and the cloud clone always load them from one commit; only the installed copy can skew, since each plugin is updated on its own (`claude plugin update <plugin>@wiki-tools`, `docs/setup.md`). `interface` covers that case: one integer in the core and in each reader's manifest, raised only when the reader format or a contract operation the notes map changes, never per release. `plugin.json` stays without a `version`. Whether `dependencies` accepts an entry without `version` is confirmed in check 2; if it doesn't, the range is a formality (`*` or the same fixed version in both) and `interface` still does the work.

**Settings: clean already.** Rules reach the wiki through the binding: `/wiki:bind-reader` copies them from the reader into the instance file (protected, installed by the user), and `sources.sh settings` and `check-settings` read only the instance, with no lookup at run time. Needed: `reader_allow` (**Before the spike**, done); optionally, `check-settings` saying "rebind needed" when the reader's manifest differs from the binding (a newly denied write tool).

**The guard: finding the reader, later.** A reader with guard fields (`scripts`, `guard_words`, `protected`) needs the guard to read its manifest at hook time, so the guard needs the reader's folder, which differs by layout and must never come from wiki data. Teams has no guard fields (**What Teams tests of it**), and the guard already protects a reader's folder in every layout (check 1), so this spike leaves finding the reader to the first reader with guard fields (**Later**). What that design must meet, from this round:
- **Which reader, from the instance; where, never.** The instance names its reader (`reader_plugin: <name>`, kebab-case, validated before any path is built from it); the location comes from the guard's own place.
- **Siblings of the guard's own plugin:** `<clone>/plugins/<name>/` in the clone and cloud layouts, where the folder is always on disk and so says nothing about whether the plugin is enabled; in the cache, the `installPath` of `<name>@wiki-tools` in `installed_plugins.json`, which may hold several project-scope entries (pick this wiki's project path), a file Claude Code describes but doesn't offer to hooks.
- **Registration** by a SessionStart hook in the reader: a hook is code, and it fails open on a timeout unless it sets `onFailure: "block"`, the objection below. The registry entry would need checking (its path under the guard's own marketplace cache or clone) and protecting from the model and from other plugins' hooks; plus its key, stale entries after a disable, and SessionStart running again on `/clear` and resume.
- **A narrower stop than "broken".** Today a broken source file stops the whole wiki: every shell and write call and every MCP tool any binding names (`set_broken`, `broken_sources`, `reader_tools`), with a message pointing to `install-source-file.sh`. A disabled reader, or a cloud environment without it, must stop only its own instance's bound tools, with its own message.

**Why not a reader hook.** A reader's own PreToolUse guard could add refusals only, never the exceptions a reader with scripts needs (deny wins); it fails open on a timeout by default; it costs a process on every tool call (on Windows the 100–250 ms Python start ADR 4 is about); and it would stand outside the core's fail-closed handling of broken sources and its Windows and Git Bash path forms. A restriction the format can't express is a reason to add a field to the format, not to ship a hook.

**Where it stops being clean.** The format is closed: a reader that needs a new kind of rule needs a generic core change first. Finding the reader at hook time rests on a file or a hook pattern Claude Code doesn't document as an interface. The Atlassian dispatcher limit is a restriction, which a reader hook could add, and its draw there is holding the limit under the connector's cloud name; a core field can do that only if the guard reads the pair table, which ADR 17 keeps out of the guard (`sourcelib.py` alone reads it). Open: the guard reads the table (an ADR 17 change), or the Atlassian reader is the one case for a reader hook. And `dependencies` makes a compatible `wiki` enabled but doesn't tell a reader's script where `wiki`'s Python is (**Later**).

**What Teams tests of it.** After the cut, `teams-reader` needs settings rules (bind time) and protection for its notes, no exceptions and no restrictions: it tests protection as it is, `dependencies`, `interface`, finding the notes by plugin name and the stop at Check, not the guard fields or finding a reader at hook time. Those are first used by a reader with code (`gws`: `scripts`, `guard_words: gws`, `~/.config/gws/` protected; the Atlassian limit).

## Spike checks

Each check records what was run, on which platform and Claude Code version, and the result, in **Findings**. Live checks use a throwaway wiki and a test folder with made-up content; nothing personal goes into this page. The prototype lives on a spike branch and is not merged. Layouts: the clone, the installed copy (`~/.claude/plugins/cache/…`, where the two plugins may sit at different versions) and the cloud clone.

1. **The notes are protected as they are** (first). Confirm with fixtures that today's guard refuses shell and Write on `teams-reader`'s files in each layout: the clone and the cloud clone (the protected clone), the installed cache (the `.claude/plugins` segment), in Git Bash and Windows path forms; another marketplace's plugin is covered the same way, the user's `~/.claude/skills` stays open. The one gap to settle: `CLAUDE_CONFIG_DIR` or `CLAUDE_CODE_PLUGIN_CACHE_DIR` pointing outside a `.claude` folder, where the cache has no protected segment (protect the cache root the guard's own path shows, or document the gap). No guard change otherwise.
2. **Two plugins, enabled per wiki.** Enable `wiki` and `teams-reader` in a test wiki's `.claude/settings.json`; both load, `teams-reader`'s `dependencies` on `wiki`, with no version range, behaves as documented (accepted without `version`, installed with it, disabled when `wiki` is disabled), and the notes skill shows in the session's skill list. `wiki` stays unversioned (**The injection interface**). A wiki without `teams-reader` loads `wiki` alone; a Teams instance there stops at Check, for that instance only (the contract's neutral message: "the reader plugin this instance names isn't loaded; see `reader_plugin`"), and the guard doesn't treat it as a broken source, so the wiki's other sources, lint and saving keep working.
3. **Binding finds the notes.** `/wiki:bind-reader` reads the contract's `## Bind` today. The reader is chosen by name, never by a skill's description, which any skill from any marketplace or `~/.claude/skills` could claim: `/wiki:add-source` already records which reader the user means to use, and that becomes the plugin name. Bind-reader loads that plugin's notes skill (`<name>:<skill>`, from the `wiki-tools` marketplace), checks its manifest's `serves` and `interface`, and follows its mapping, denies and rules. The binding it produces (`reader`, `reader_deny`, `reader_allow`, and `reader_plugin: <name>` in the frontmatter, the one marker Check and the guard read) matches today's rules exactly. **Parity for a binding made without notes:** today the contract always hands bind-reader the Outlook and people denies, several of them read tools (`get_me`, `search_people`, `outlook_email_search`) that its "looks like a write" rule wouldn't catch. A binding of the Microsoft 365 connector without `reader_plugin` must be detectable, and Check then refuses it or asks for a rebind; the denies the type always needs stay in the contract if that can't be done. Fixtures: a binding without notes, a plugin whose `serves` or `interface` doesn't match.
4. **The notes in an ingest.** The instance's `reader_plugin` names the reader. `/wiki:ingest` loads it at Check with no prompt and follows its quirks (chat paging, reply truncation, the folder paging) through List new and Fetch. Check whether a plugin skill needs a permission rule (`Skill(...)`) and whether `wiki:ingest`'s `allowed-tools` would have to name it (it may not, by the one-way rule; then the rule goes into `reader_allow`). Repeat it unattended (`/wiki:ingest all --unattended`), where nothing may prompt.
5. **Version skew** (installed layout only; the clone and the cloud clone keep both plugins at one commit). Decided 2026-11-28: `interface` only, no semver (**The injection interface**). The check confirms it holds: with `teams-reader` older or newer than `wiki` (an operation the contract renamed, a binding field the core doesn't know), Check compares the manifest's `interface` with the core's and stops only the Teams instance, with a message to update both plugins; with the same `interface`, the older reader still works. Fixtures for both. The README says to update `wiki` and `teams-reader` together.
6. **Copilot CLI** (desk check only; Teams in Copilot is parked). Whether Copilot loads a second plugin and its skills; a follow-up, not a go criterion.
7. **Cloud.** The cloud ignores a wiki's `enabledPlugins`, so loading `teams-reader` loads it for every wiki in that environment: add it only in environments whose wikis have a Teams instance, and find whether `CLAUDE_CODE_PLUGIN_DIRS` takes two folders (separator, order). Both come from the one clone `cloud-update.sh` keeps current (ADR 19). A cloud routine on a bound Teams wiki loads the notes, shows the cloud-name denies in effect and runs the walk and snapshot with no prompt (the cloud connector baseline is itself still pending live checks, `cloud/SETUP.md`).
8. **Migration.** An existing bound instance keeps its `reader`, `reader_deny`, `files.tsv` and settings; it gains `reader_plugin: teams-reader` (and whatever check 3 requires of a binding made without notes), added by `/wiki:bind-reader` or a named manual step. Without `teams-reader` enabled, Check says so. Nothing about the snapshot changes.
9. **Repo plumbing and docs.** The marketplace lists both plugins; `tests/test_agent_files.py` is extended to plugin skills (it scans only `.claude/skills` today); a new test checks that nothing under `plugins/wiki/` names `teams-reader` (`test_source_neutral.py` scans scripts, hooks and templates, not contracts or skills). The contract's connector mentions are listed, each moved or kept as neutral policy, and the slimmed contract is checked to name no connector tool. A draft `plugins/teams-reader/README.md` holds the whole enabling flow, so a user needs no other page:
    1. Add the source: `/wiki:add-source` for `ms-teams` (the user's step).
    2. Enable the reader in that wiki only: `claude plugin install teams-reader@wiki-tools --scope project` (from a clone: `claude plugin enable … --scope project`), then restart `claude`; it writes `enabledPlugins` in the wiki's `.claude/settings.json`.
    3. Bind: `/wiki:bind-reader <key>`, which writes `reader`, `reader_deny`, `reader_allow`, `reader_plugin` and `## Reader`.
    4. Settings: `sources.sh settings ms-teams --key <key>`, installed in the wiki's settings (committed, for a cloud routine); `check-settings` confirms.
    5. Ingest: `/wiki:ingest` (the user's step); without the plugin, Check stops with its message.
    6. Remove: delete the instance, remove the rules `check-settings` reports as stale, `claude plugin disable teams-reader@wiki-tools --scope project`.
    7. Cloud: add `teams-reader` to the environment's `CLAUDE_CODE_PLUGIN_DIRS`, only for environments whose wikis use Teams.
    8. Update: `claude plugin update` both `wiki@wiki-tools` and `teams-reader@wiki-tools`, together; a mismatched `interface` stops the Teams instance at Check.
    9. Migration from a wiki bound before the move.

    Links to it from `README.md` (its source-type list), `docs/setup.md` (its Microsoft Teams entry) and `docs/sources.md`. The README's steps are the ones the live tests follow, so a run checks the docs too.

## Pattern for the other sources

The spike is meant as the pattern for moving other readers' notes out of the core. A go here doesn't move them; each would be its own plan.

**Two layers.** Every tool reader is a base reader plus a wiki reader plugin:
1. **Base reader:** generic, knows nothing of wikis, usable in any session, and owns its sign-in and scope. A claude.ai connector (Teams, Gmail, Drive, Jira), another marketplace's plugin (`proton`), or the user's own skill or CLI under `~/.claude/skills` (OneNote). It is not shipped here and stays the user's.
2. **Wiki reader plugin** (`<type>-reader`, this marketplace): the adapter's notes. It maps the contract's operations to the base reader's tools or commands, with fixed arguments, denies, auxiliary rules and quirks. It depends one way on `wiki` and on the base reader's **interface**, never on its code; its README documents that interface, so any base reader that meets it can be bound.

| Type | Plugin | What would move | Needs beyond this spike |
|---|---|---|---|
| `gmail` | `gmail-reader` | `## Bind` mapping, fixed arguments, denies, connector quirks | nothing; the simplest second case |
| `google-drive` | `google-drive-reader` | mapping, denies, quirks (`decode-download.sh` stays core) | nothing; its cloud name is still unknown (`connectors.md`), so it can't run in the cloud either way |
| `jira` | `jira-reader` | mapping, `executeRead` arguments, denies, quirks | to use the dispatcher operations in the cloud, a generic way to hold the `field=value` limit under the cloud name (today denied there, which is parity): the guard reads the pair table, or a reader hook (**Where it stops being clean**) |
| `proton-files` | `proton-files-reader` | Proton-specific commands, arguments, quirks | the external `proton` plugin is its base reader and stays the user's install; its command allow, hand-written in user settings today, goes into the instance's `reader` (operation bindings; `reader_allow` takes only a helper-script or cache allow, anything else needs a new named shape first) |
| `onenote` | `onenote-reader` | the operation mapping and Bind tests against a defined base-reader interface (`notebooks`, `sections`, `pages`, `page`, `files`, GET only), the scope check, Graph quirks | a base reader meeting that interface; its reader's rules (`Bash(<reader command> *)` or `mcp__…` read tools) go into the instance's `reader`; `reader_allow` takes only a helper-script or cache allow, anything else needs a new named shape first (**Before the spike**). A token-taking script shipped here (`docs/plans/onenote-cloud.md`) would be code (**Later**) |
| `codebase`, `local-folder` | none | stay core | — |

`codebase` and `local-folder` are `access: filesystem` types: their wrappers are the source's read-only access, not a separate reader, and `codebase`'s `agent_only` and root checks are core guard checks. They stay in the core.

## Later: readers with code

A reader plugin that ships scripts or guard fields (a `gws` wrapper, a OneNote reader script, the Atlassian dispatcher limit) needs what this spike leaves out. Its own plan takes these on, and moving the snapshot can be reconsidered then:
- **A launcher across layouts:** `dependencies` makes a compatible `wiki` enabled, but the plugin's Python must still find a compatible `wiki` root (for `contract`, `sourcelib`) with no fixed path, under `-I` and without `.venv`, and fail clearly when `wiki` is missing or at another version. It also needs an amendment to ADR 4 for Python outside `plugins/wiki/`.
- **A guard exception for a trusted reader root:** a script under a sibling plugin the guard trusts, with today's plain-call checks (lookalikes, chained and redirected calls, `..`, PowerShell). The root is trusted from the guard's own location, never from wiki data. The manifest's `scripts` field carries the exception.
- **Finding the reader at hook time**, under the constraints in **The guard: finding the reader, later**: the instance names the reader, the location comes from the guard's own place, and a missing reader stops only its instance.

## Out of scope

Moving the snapshot or the walk; new enforcement (no URI limit on `read_resource`); any hook or script in `teams-reader`; any guard change beyond check 1's gap; finding a reader at hook time; other Microsoft 365 sources (Outlook, OneNote); the Atlassian dispatcher limit; readers from other marketplaces; pruning the walk by folder size (#82); a Graph reader; keeping the snapshot across cloud VMs; Teams in Copilot.
