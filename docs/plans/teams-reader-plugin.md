# Spike: a Teams reader plugin for `ms-teams`

The Teams half of the roadmap item **Reader plugins for connector workarounds**: move everything specific to reading Teams with the claude.ai Microsoft 365 connector out of the core `wiki` plugin into a second plugin, `teams-reader`, in the wiki-tools marketplace. It serves only the `ms-teams` source type. This page plans a spike that answers whether that works and with what shape; it builds nothing that is merged, and no-go is an acceptable outcome. The Atlassian half (the dispatcher limit, `docs/adr.md`, 11) and readers from other marketplaces (**Readers from installed plugins**) stay parked.

## Principles

- **One repo, separate plugins.** Every reader plugin lives in this repo, under `plugins/<type>-reader/`, and is listed in this repo's marketplace (`.claude-plugin/marketplace.json`) beside `wiki`. Each is installed on its own, per wiki: `claude plugin install <type>-reader@wiki-tools --scope project`. They share the repo's CI, lint, tests, personal-data check and review; readers from other marketplaces stay parked. This also bounds gate 2: the guard only has to trust plugin roots of its own marketplace.
- **One-way dependency.** `teams-reader` may use `wiki` (its scripts, its contract, its skills); no code, skill or contract in `wiki` names `teams-reader`. `wiki` alone keeps working, and ADR 1 still holds for it. The repo's user docs link to `teams-reader`'s README (check 11); a link is documentation, not a dependency.
- **Parity, not stricter or looser.** Every protection, allow and deny rule a bound Teams instance has today it still has; nothing new is enforced (no URI limit on `read_resource`).
- **Settings first, the guard where it is today** (`docs/adr.md`, 3). Allow and deny stay settings rules, generated by `sources.sh settings` and verified by `check-settings`. Bash allow rules don't replace the guard's path checks (ADR 3), so the snapshot keeps today's plain-call checks through a generic, data-only exception in the core guard. `teams-reader` has no guard of its own, and the core guard imports nothing from it.
- **The binding owns reader-specific rules.** Rules only this reader needs (the snapshot allow) live in the instance's binding, not in the core contract, so they reach a wiki's settings only for a bound instance.
- **Only where Teams is added.** Locally, `teams-reader` is enabled in a wiki's `enabledPlugins` only when that wiki has an `ms-teams` instance, and ships no settings. In the cloud, `enabledPlugins` doesn't apply (check 7).
- **The core stays generic.** The core names no Teams tool, server or script (`tests/test_source_neutral.py`); its remaining Teams parts are data: the tool-neutral contract and the cloud-name pair.

## Why now (changes since the roadmap item, 2026-11-22)

- ADR 2 was sharpened (2026-11-25) and is checked by `tests/test_source_neutral.py`; reader details go in the contract, the binding, or a reader plugin.
- ADR 17: cloud names for concrete MCP bindings and denies come from `sources/connectors.md`, read only by `sourcelib.py`.
- Cloud wikis: the setup script copies only `plugins/wiki/` to `/opt/wiki-plugin` (`CLAUDE_CODE_PLUGIN_DIRS`); the cache starts empty in each VM.
- Wiki-local skills (#110) are an alternative home for a reader skill, per wiki.
- Connector tools opt-in (planned): `teams-reader`'s tools must fit it once it exists.

## Spike checks

Each check records what was run, on which platform and Claude Code version, and the result, in **Findings**. Live checks use a throwaway wiki and a test folder with made-up content; nothing personal goes into this page. The prototype lives on a spike branch and is not merged. Layouts: the clone, the installed copy (`~/.claude/plugins/cache/…`, where the two plugins may sit at different versions) and the cloud copy; every gate holds in all three.

**Gates (run first; any failure is a no-go):**

1. **The moved script runs.** `py-run.sh` runs the Python file beside it, adds its own folder to `sys.path`, runs under `-I` (no `PYTHONPATH`), and `.venv` is dev-only. Show how `teams-reader`'s launcher resolves the active, compatible `wiki` root without a fixed path, launches its own module with `wiki`'s `contract` and `sourcelib` importable, and keeps the full instance validation. Prove it without `.venv`, with the roots in separate places, and with `wiki` missing or at an incompatible version (a clear error, not a silent run). The guard's `..` refusal concerns the model's call, not this lookup.
2. **Guard parity.** Removing `scripts/file-snapshot.sh` from `CORE_SCRIPTS` drops its lookalike check and the plain-call checks; a protected root alone would refuse the real call too. Add a generic, data-only exception: a script the bound instance declares, under a reader root the guard trusts. Settle first how the root is trusted (not from binding data alone: an instance file is wiki content). Then show the real launcher passes, and lookalikes, chained and redirected calls, `..` forms, PowerShell calls, and shell and Write on the root's files stay refused, on Windows and Git Bash path forms, in each layout.
3. **Binding-owned rules.** `reader` holds only operation bindings; `read_tools` applies by type, also to unbound instances, and must not name a plugin. Add a validated binding field for auxiliary rules (the snapshot allow; a `Skill(...)` rule if check 6 needs one), emitted by `settings --key`, checked by `check-settings`, and reported by `stale_rules` once the last binding using it is gone (today the old snapshot allow is deliberately not reported, `tests/test_sources.py`, ~227–240). Tests: no binding, a missing rule, the last binding removed. Locally a rule in user settings satisfies `check-settings`; a cloud routine needs it in the wiki's committed settings, so `check-settings` says which.

**Then:**

4. **Two plugins, enabled per wiki.** Enable `wiki` and `teams-reader` in a test wiki's `.claude/settings.json`; both load, and `${CLAUDE_PLUGIN_ROOT}` in a `teams-reader` skill is its own folder. A wiki without `teams-reader` loads `wiki` alone; a Teams instance there fails clearly at Check, not silently.
5. **Binding finds the reader's notes.** `/wiki:bind-reader` reads the contract's `## Bind` today. Find a generic way it discovers a reader plugin's mapping, denies and rules without the core naming it (e.g. a reader skill the model loads when binding). The binding it produces (`reader`, `reader_deny`, the field from check 3, `## Reader`) matches today's rules.
6. **The walk skill in an ingest.** The instance's `## Reader` names the walk skill; `/wiki:ingest` starts it mid-run with no prompt and continues; it calls only the bound **list folder** tool and writes `walk.tsv`; the contract's List new then runs compare, its own steps 3–4, and save after the pages. Whether a plugin skill has a permission rule (`Skill(...)`) and whether `wiki:ingest`'s `allowed-tools` must name it (it may not, by the one-way rule).
7. **Cloud.** The cloud ignores a wiki's `enabledPlugins`, so copying `teams-reader` loads it for every wiki in that environment: copy it only into environments whose wikis have a Teams instance, and find whether `CLAUDE_CODE_PLUGIN_DIRS` takes two folders (separator, order). A cloud routine on a bound Teams wiki shows the cloud-name denies in effect, runs the walk and snapshot with no prompt, and behaves as today on the empty cache (the cloud connector baseline is itself still pending live checks, `cloud/SETUP.md`).
8. **Migration.** An existing bound instance keeps its `reader`, `reader_deny` and `files.tsv`; it gains the binding field and the walk skill line; the first compare after the move reports the same changes; the old `Bash(bash */scripts/file-snapshot.sh *)` allow is removed, by `check-settings` or a named manual step. Instances whose reader has modified times need nothing. A non-connector `ms-teams` reader without modified times still gets the snapshot (fixture, `tests/test_file_snapshot.py`, ~80–93).
9. **Copilot CLI** (desk check only; Teams in Copilot is parked). Whether Copilot loads a second plugin and its skills; a follow-up, not a go criterion.
10. **Repo plumbing.** The marketplace lists both plugins; `teams-reader`'s tests run in `bash tests/run-tests.sh` and its Python in `dev-lint.sh` (mypy); `tests/test_agent_files.py` is extended to its skills (it scans only `.claude/skills` today); a new test checks that no code, skill or contract under `plugins/wiki/` names `teams-reader` (`test_source_neutral.py` doesn't scan contracts for it).
11. **Docs.** A draft `plugins/teams-reader/README.md` holds the whole enabling flow, so a user needs no other page:
    1. Add the source: `/wiki:add-source` for `ms-teams` (the user's step).
    2. Enable the reader in that wiki only: `claude plugin install teams-reader@wiki-tools --scope project` (from a clone: `claude plugin enable … --scope project`), then restart `claude`; it writes `enabledPlugins` in the wiki's `.claude/settings.json`.
    3. Bind: `/wiki:bind-reader <key>`, which writes `reader`, `reader_deny`, the rules field and `## Reader`.
    4. Settings: `sources.sh settings ms-teams --key <key>`, installed in the wiki's settings (committed, for a cloud routine); `check-settings` confirms.
    5. Ingest: `/wiki:ingest` (the user's step); without the plugin, Check stops with its message.
    6. Remove: delete the instance, remove the rules `check-settings` reports as stale, `claude plugin disable teams-reader@wiki-tools --scope project`.
    7. Cloud: the environment's setup copies `teams-reader` beside `wiki`, only for environments whose wikis use Teams.
    8. Migration from a wiki bound before the move.

    Links to it from `README.md` (its source-type list), `docs/setup.md` (its Microsoft Teams entry) and `docs/sources.md`; the contract's Check message stays neutral ("no reader for this instance; see its `## Reader`"). The README's steps are the ones the live tests (below) follow, so a run checks the docs too.

## E2E tests

Two levels, both part of the go criteria.

**Automated, in CI** (`bash tests/run-tests.sh --e2e`, Linux and Windows; fakes only, no real connector or account, as for every repo test). Each builds a throwaway wiki in `tmp_path` with both plugins loaded from the clone's layout and a bound `ms-teams` instance, then runs through the real launchers:
- the snapshot through `teams-reader`'s launcher: `compare` and `save` on a fake `walk.tsv`, first run and a changed second run, with the result `test_file_snapshot.py` expects today; with `wiki` missing or incompatible, a clear error (gate 1);
- the guard through `py-launch.sh`: the real call passes; lookalikes, chained and redirected calls, `..`, PowerShell, and shell and Write on the reader root refused, for the clone and an installed-cache layout (gate 2);
- `sources.sh settings ms-teams --key` and `check-settings`: today's rules plus the snapshot allow; a missing rule reported; the last binding removed, its rules reported stale (gate 3);
- a wiki without `teams-reader`: `wiki` alone passes its tests, and a Teams instance's Check fails with its message (check 4);
- migration: an instance and settings from before the move, upgraded, with the same compare result (check 8).

**Live, in real wikis** (by hand, before go; not in CI). Real Claude Code sessions with the real guard, in throwaway wikis set up by following the README draft step by step, against a test team and SharePoint folder with made-up content and the claude.ai Microsoft 365 connector. Linux in the disposable container (`tests/live/`, extended with a `teams-reader` lane; whether the connector signs in there is itself a check) and Windows (Git Bash) on a developer machine:
- **W1, Teams wiki:** steps 1–5 of the README; the first ingest walks, snapshots and writes pages with no prompt beyond the user's steps; a second ingest after a file is added, changed and removed reports exactly those.
- **W2, a wiki without Teams** on the same machine: `teams-reader` doesn't load, no Teams rules in its settings, `/wiki:init`'s check (`wiki-check.sh`) clean.
- **W3, protection:** in W1, prompts that try a lookalike snapshot, a chained call, and an Edit of a `teams-reader` file; the guard refuses each.
- **W4, removal:** step 6 in W1; `check-settings` reports the stale rules, and after the disable the plugin no longer loads.
- **W5, migration:** a wiki bound with today's `wiki` (old allow, contract walk), moved by step 8; the next ingest matches.
- **W6, cloud:** a cloud routine on W1's committed settings (check 7).

Steps that start a manual-only skill (`/wiki:add-source`, `/wiki:ingest`, `/wiki:init`) are the user's; Claude runs `/wiki:bind-reader`, `sources.sh`, `check-settings` and `wiki-check.sh`. Each run adds a line to a results file like `tests/live/results.md` (Claude Code version, platform, case, outcome); session IDs, tenant and folder names, and other personal data stay out of it.

## What the spike decides

- **Go** if gates 1 to 3 hold in every layout on Linux and Windows, checks 4 to 8 and 11 pass, check 7 with a Teams-only cloud routine, the automated e2e tests are green in CI and the live cases W1–W6 pass on both platforms (W6 on Linux). **No-go** otherwise: the Teams parts stay in `wiki` and the Teams part of the roadmap item closes.
- For a go: the layout, how the launcher finds `wiki` (gate 1), how the guard trusts a reader root (gate 2), the binding field (gate 3), how bind-reader discovers reader notes (check 5), the cloud setup (check 7), and a build plan (a revision of this page) with its tests (the e2e tests above kept, the live cases as a release check), the ADR amendments (1 for a second plugin, 2 and 22 for where reader details and the snapshot live, 3 and the guard ADRs for the reader-root exception, 4 for Python outside `plugins/wiki/`, 13 for the binding field) and the docs to update.

## Pattern for the other sources

The spike is meant as the pattern for moving other readers out of the core. A desk check of each source type against it (2026-11-26) found none that conflicts with its principles. A go here doesn't move them; each would be its own plan.

**Two layers.** Every tool reader is a base reader plus a wiki reader plugin:
1. **Base reader:** generic, knows nothing of wikis, usable in any session, and owns its sign-in and scope. A claude.ai connector (Teams, Gmail, Drive, Jira), another marketplace's plugin (`proton`), or the user's own skill or CLI under `~/.claude/skills` (OneNote). It is not shipped here and stays the user's.
2. **Wiki reader plugin** (`<type>-reader`, this marketplace): the adapter. It maps the contract's operations to the base reader's tools or commands, with fixed arguments, denies, the Bind test sequence and quirks, plus any wiki-specific traversal or script (Teams' walk and snapshot). It depends one way on `wiki` and on the base reader's **interface**, never on its code; its README documents that interface (commands or tools, their output, read-only), so any base reader that meets it can be bound.

Base-reader rules go into the instance's `reader`/`reader_deny` and so are emitted by `sources.sh settings` and checked by `check-settings`, the same rules as today, generated rather than hand-written. The guard needs nothing new for a base reader: connector tools are settings rules, and the user's `~/.claude/skills` scripts already run (`guard.py`, ~163). A base reader outside the connectors isn't in a cloud VM, so the environment setup must provide it, as today.

| Type | Plugin | What would move | Needs beyond this spike |
|---|---|---|---|
| `gmail` | `gmail-reader` | `## Bind` mapping, fixed arguments, denies, connector quirks | nothing; the simplest second case |
| `google-drive` | `google-drive-reader` | mapping, denies, quirks (`decode-download.sh` stays core) | nothing; its cloud name is still unknown (`connectors.md`), so it can't run in the cloud either way |
| `jira` | `jira-reader` | mapping, `executeRead` arguments, denies, quirks | to use the dispatcher operations in the cloud, a generic way to hold the `field=value` limit under the cloud name (today denied there, which is parity) |
| `proton-files` | `proton-files-reader` | Proton-specific commands, arguments, quirks | the external `proton` plugin is its base reader and stays the user's install; its allow, hand-written in user settings today, goes into the binding. Trusting another marketplace's plugin root stays parked (**Readers from installed plugins**) |
| `onenote` | `onenote-reader` | the operation mapping and Bind tests against a defined base-reader interface (`notebooks`, `sections`, `pages`, `page`, `files`, GET only), the scope check, Graph quirks; the section trigger and text comparison stay contract policy (as Teams' List new steps 3–4 do) | a user base reader under `~/.claude/skills` meeting that interface; its rules move from "allow them yourself" (Caveats) into the binding |
| `codebase`, `local-folder` | none | stay core | — |

`codebase` and `local-folder` are `access: filesystem` types: their wrappers are the source's read-only access, not a separate reader, and `codebase`'s `agent_only` and root checks are core guard checks. They stay in the core.

## Assessment (2026-11-26)

**For separate readers:** the core no longer changes when a connector does (renamed tools, cloud names, quirks), and readers ship on their own schedule; a wiki loads only the readers it uses; the base-reader interface lets a CLI, another connector or `gws` bind to the same plugin; rules that are hand-written today (the snapshot allow, OneNote's reader rules) become generated and checked; the pattern fits every tool reader with small generic additions.

**Against:** the trusted-reader-root exception is new code in the most sensitive part, and today's safety rests on one protected folder; `wiki` and the readers can sit at different versions in the plugin cache, so launchers must find a compatible `wiki`; one more install per wiki, a "reader missing" failure, and a harder cloud setup (`enabledPlugins` doesn't apply there); fakes, e2e and live runs per reader on two platforms; `/wiki:bind-reader` finding a reader's notes without naming it relies on the model loading a skill; more ADRs and docs spread over plugins. And the gain is small today: the core is already tool-neutral (ADRs 2, 22), and for Teams what moves is mostly prose plus one script.

**Recommendation:**
1. Do the generic parts that pay off with or without plugins first, each as its own change: the binding field for auxiliary rules (gate 3), which also moves OneNote's reader rules into the binding.
2. Time-box this spike, with gate 2 (how the guard trusts a reader root) as the deciding question.
3. Build reader plugins once a second reader brings real code (`gws`, a OneNote base reader), the parked row's trigger.

## Out of scope

New enforcement (no URI limit on `read_resource`; its use on listed items only stays the contract's rule, as today); a guard in `teams-reader`; other Microsoft 365 sources (Outlook, OneNote); the Atlassian dispatcher limit; readers from other marketplaces; pruning the walk by folder size (#82); a Graph reader; keeping the snapshot across cloud VMs; Teams in Copilot.
