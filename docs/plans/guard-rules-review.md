# Plan: guard checks only where Claude's permission rules fall short (#24)

Scope: **Claude Code only.** Copilot CLI support is not part of this plan (no Copilot adapter, no `--deny-tool`, no parity tests); that work stays in `docs/plans/copilot-wiki-support.md`. So the principle's "for both clients" becomes "in Claude Code's `settings.json`", and the issue's code-design comment is cut down to what Claude needs (step 2).

## The principle (amends `docs/adr.md`, 3)

> A protection goes into the wiki's Claude Code permission rules (`.claude/settings.json`, from `templates/project-settings.json` and `sources.sh settings`) when it can be expressed there reliably. A guard check is added only when it can't, and only when the harm it prevents justifies its maintenance cost. Irreversible harm (`git push`, writes into a source) stays guarded by a deterministic check even where a rule also covers it; checks fed by the source contracts (guard words, roots, agent_only) stay in the guard, since no rule knows them at hook time.

Limits of rules that decide most rows (to confirm in step 0):
- **R1** Committed settings can't name a per-machine path (the plugin folder; `docs/adr.md`, 1).
- **R2** `Read`/`Edit` rules apply to the file tools only, not to Bash (`cat`, `sed -i`, `>`).
- **R3** `Bash(...)` rules match the command's shape, per subcommand: Claude Code splits `&&`, `;`, `|` and checks each part, so `cd x && git push` is caught. They miss options before the subcommand (`git -C x push`, `git -c k=v push`), `sh -c "…"`, `$(…)` and `eval`. Whether leading `VAR=` and wrappers (`timeout`, `nice`, `env`) are stripped, and whether `Bash(git push *)` matches a bare `git push`, is for step 0.
- **R4** Rules apply to the main session and subagents alike, so they can't express agent_only.
- **R5** Rules are static: a change to a contract or an instance needs the user to regenerate the wiki's settings, and existing wikis keep the old rules until they do (`sources.sh check-settings` / `wiki-check` report the gap). The guard reads contracts at hook time.
- **R6** A plugin can't ship permission rules into a wiki; every rule lives in each wiki's settings.

The rule limits:
- **R1** stands: path patterns are `//abs`, `~/…`, `/…` (relative to the settings file's project, or `~/.claude/` in user settings) and relative to the cwd (S1); nothing names a plugin folder.
- **R2** partly wrong: `Read`/`Edit` deny rules also apply to file commands Claude Code recognizes in Bash (`cat`, `head`, `tail`, `sed`, `tee`) and to redirect targets (`> f`, `< f`), but not to other programs (`cp`, a Python script) or a command that reads without naming the file (`grep -r x .`) (S1). Doesn't change a decision: no second-layer rules.
- **R3** confirmed in detail (S1): `*` matches any text, and a trailing ` *` also matches the bare command, so `Bash(git push *)` matches `git push`. Compound commands are split at `&&`, `||`, `;`, `|`, `|&`, `&` and newlines, and a deny rule also applies inside subshells, `$(…)`, backticks and loop bodies. Stripped before matching: the wrappers `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, zsh's `noglob`, bare `xargs`; for deny rules, any leading `VAR=` assignment. Not matched: options before the subcommand (`git -C . push`, `git -c … push`), `sh -c`/`bash -c`, an absolute path to the program, `env`, other runners. `eval` isn't mentioned.
- **R4** confirmed: subagents inherit the parent's permission rules (S4, sub-agents).
- **R5** stands (rules are settings; nothing in the docs reads them per call from other files).
- **R6** confirmed: a plugin's components are skills, commands, agents, hooks, MCP and LSP servers, output styles, workflows, themes, monitors and `bin/`; there is no plugin settings file, and `plugin.json` strips unknown top-level keys (S4). A plugin can't ship `permissions`.

Other questions:
- **Case:** PowerShell rules are case-insensitive (S1). For Bash and Read/Edit rules, and for hook matchers, the docs don't say (open).
- **Hook matcher:** a matcher of only letters, digits, `_`, `-`, spaces, `,` and `|` is a list of exact names; anything else is an unanchored JavaScript regex; `*`, `""` or no matcher matches every tool (S2). Ours (`Bash|PowerShell|Write|Edit|MultiEdit|Read|Grep|Glob`) is an exact list.

### Needs the maintainer
- **Row 16, Monitor:** the plan says Monitor's command passes the guard today. Per S2 it doesn't on Claude Code v2.1.314 or later: our matcher names `Bash`, so the guard already runs on Monitor's shell commands, seen as a Bash call. The decision (match every tool, classify) still works, but with a matcher that includes Monitor (or every tool) the hook gets Monitor's own input (`tool_name` "Monitor"), so the classifier must treat Monitor as a shell tool, and decide on a WebSocket watch (`ws`, no `command`): refuse (fail closed, as a shell call without a command), or pass as harmless. Before v2.1.314, Monitor is unguarded with the current matcher.
- **Row 16, NotebookEdit:** its path field is `notebook_path`, and its content `new_source`; `hookjson.parse` must read both for the write checks.
- **Row 17, git config:** step 1 recommends refusing `git config` writes (any `git config` other than `--get`/`--list`/`-l`/`--get-regexp`/`--show-origin` reads) and `git -c` outright, and the `GIT_CONFIG_*` variables, instead of a list of keys.
- **Row 10:** `file_path` reaches the hook absolute, so only an absolute path with `..` inside could get past; the fix stays useful but its relative-path fixture can't happen in a real session.

## Decisions (maintainer, 2026-11-18)
- **Rows 1–4, 7–11, 13–15:** keep, with the fixes above (row 4 trailing slash, row 10 `..` via `abs_path`).
- **Row 5:** Write/Edit/MultiEdit (and NotebookEdit) refuse the whole plugin folder in every spelling, as shell does.
- **Row 6:** drop `hooks.json` and `disableAllHooks`; refuse any shell command that starts a nested `claude` session (covers `claude plugin`). Match `claude` as a command word (start of the command or after `; & | ( $(` backtick, `env`, `exec`, `command`), never as text: `.claude/` is in many legitimate paths. Both removals are stated in the commit message.
- **Row 12:** keep the chained-call message.
- **Row 16:** the matcher catches every tool; the guard classifies: shell tools (Bash, PowerShell, Monitor) get the command checks, file writers (Write, Edit, MultiEdit, NotebookEdit) the write checks, Read/Grep/Glob as today, a known-harmless list and `mcp__*` pass, any other name is refused with a message naming the tool. Step 1 confirms each built-in tool's name and input fields from real hook payloads; time per call measured (every tool now launches the guard).
- **Row 17:** protect `.git/hooks`, `.git/config`, `.mcp.json`, `.claude/skills` and `.claude/agents` (shell and Write). Also needed so `.git/hooks` can't be sidestepped: refuse `hookspath` in shell commands (`git config core.hooksPath …`, `git -c core.hooksPath=…`), and `git config alias.` (a `!` alias can run anything). Step 1 checks for other git config keys that run commands (`core.fsmonitor`, `core.sshCommand`, `diff.external`, filters) and decides whether to refuse `git config` writes outright instead of a list.
