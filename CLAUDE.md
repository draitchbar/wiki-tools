# wiki-tools

Shared tooling for the LLM wikis: a local-directory plugin marketplace with one plugin, `wiki`, which also carries the shared schema it loads into every wiki session.

This repo is maintained in a Claude session opened here, where the `wiki` plugin is **not** enabled. The guard hooks are active only inside the wikis. README.md is the quick start; the details are in `docs/` (setup, skills, sources, guard, development, layout) and the decisions in `docs/adr.md`.

## Rules for editing this repo
- Scripts are POSIX bash that must run under Linux bash and Git Bash on Windows. No `jq`, no GNU-only flags beyond what Git Bash ships (`sed`, `grep -E`, `date -d` are fine). Python (`docs/adr.md`, 4): the guard (`guard.py`, `hookjson.py`, `contract.py`, `py_version.py`), run only through `py-launch.sh`, which fails closed; and the scripts' work behind their `.sh` launchers (`sourcelib.py`, `sources.py`, `lint.py`, `wiki_check.py`, `sync_status.py`, `install_source.py`, `decode_download.py`, `sources/ms-teams/snapshot.py`), run only through `py-run.sh`; and the repo's own `scripts/pii_check.py` behind `scripts/pii-check.sh`. Standard library only, Python 3.9 or later. No other Python without a decision recorded in `docs/adr.md`.
- Keep LF line endings (`.gitattributes` enforces this). Never introduce CRLF.
- Any change to `plugins/wiki/scripts/`, `plugins/wiki/hooks/` or a wrapper in `plugins/wiki/sources/` needs a matching fixture or test (`tests/fixtures/`, `tests/test_*.py`) and a green `bash tests/run-tests.sh` before committing; a change to a launcher or another `.sh` file also a green `bash tests/run-tests.sh --e2e`. The tests are pytest (step 6, 2026-11-14; unpinned, the test runner's only dependency, never the plugin's). Tests never call a real source CLI or account; they use fakes (`tests/sources/<type>/`).
- The guards are a guardrail, not a security boundary. Don't weaken one without saying so in the commit message.
- No fixed clone path. Skills, the schema and contract bodies name plugin files as `${CLAUDE_PLUGIN_ROOT}/...` (filled in by Claude Code for skills, by `schema.sh` and `sources.sh` for the rest); scripts find their own folder; contract `read_tools` use `Bash(bash */sources/<type>/<script>.sh *)`. Everything the wikis need lives under `plugins/wiki/`, since Claude Code may run an installed copy of only that folder.
- Sources: the wiki skills are source-neutral. Anything specific to one source belongs in its type's `plugins/wiki/sources/<type>/SOURCE.md`, never in a skill. New standard types: `/new-source-type`.
- Test plans sent to a wiki session: Claude can't start a skill with `disable-model-invocation` (`init`, `add-source`, `ingest`, `lint`, `audit`, `commit-themes`): mark such a step as the user's; for `/wiki:init`'s check mode, Claude can run `wiki-check.sh` (`docs/skills.md`, `/wiki:init`).
- Remote is the GitHub repo `draitchbar/wiki-tools`, public (`docs/adr.md`, 9). `main` changes only through squash-merged pull requests; CI (`.github/workflows/ci.yml`) runs lint and the suite (`--e2e` too) on Linux and Windows, `pii.yml` the personal-data check, and Claude reviews each PR (`claude-review.yml`). Issues and PRs are for collaborators (`CONTRIBUTING.md`).
- Personal data (`docs/development.md`, "Personal data"): this repo is public, so no real names, emails, places, hostnames, employer details or third parties in files, commits, branch names or PR text. Before the first push in any clone, cloud sessions included, run `git config core.hooksPath .githooks`; never push with `--no-verify`. If the hook, a guard or the push itself is blocked or fails, stop and report it; never get around it (another remote URL, `git -c`, the GitHub API or web UI). Commit as the GitHub noreply address. Commits and PR descriptions carry no `Claude-Session:` trailer (`Co-Authored-By: Claude … <noreply@anthropic.com>` stays).
- Lint must be clean before committing: `ruff check .` (`ruff.toml`) and `shellcheck -S warning` on every `*.sh` (`.shellcheckrc`).
